## 3. 两项完整交付与本队亮点

### SKL-001：FPGA模块开发与仿真验证

唯一源码位置：`skill/fpga-module-verification/`。活动批准版与新待审候选分开；A 制作、B 复核。旧通用协作 Skill 与 0.2.0 包保留在[历史归档](../archive/2026-09-13-before-skl001-technical-upgrade/README.md)，不得恢复为活动源。能力为单时钟/组合模块开发和仿真，不绑定本队人数、题目或路径。

完整包包含：SKILL.md、竞赛README、模块接口/数值合同、RTL编码和自检TB方法、实际XSim运行器、首错调试指南、已有项目模块与非声学模块、故障/修复复测、可见交互与来源/许可、准确版本及复核入口。源码只放一处，任务包留清单、日志和输入快照；不复制整套工程。

本队主打贡献：**接口合同→RTL/TB→实际仿真→首个错误→修复复测的可复现技术闭环**。重点处理符号/位宽、采样时序、握手与背压、复位在途事务、独立golden、非零检查计数、超时及旧日志误PASS。区分开发/验收、三交接点和准确版本复核继续保留，但不再以协作制度作为主要技术产物。

B的最小行为验收（团队自设，不是官方规定数量）：

1. 复跑准确候选的runner测试及真实XSim：已有符号扩展模块与非声学elastic_stage正常通过，数据错误/ready错误在仿真阶段被检出，恢复正确源后用相同TB复测。工具启动失败不算故障检出。
2. B另给一个作者未用过的模块/合同变体及一个未知故障。在隔离上下文只给Skill、需求和必要输入，让执行方完成RTL/TB、实际运行和首错修复；不提供参考答案。不要求B再造整套工程。
3. 检查独立golden、X/Z、边界、复位、背压、延迟/吞吐、事务计数与排空、版本/日志绑定；不得以退出0或一个PASS字符串代替真实检查。缺工具报告环境问题，不编造运行。
4. 记录有无Skill或旧版/新版同输入效果及人工纠正；作者故障注入不等于AI效率改善或陌生团队复用证明。保留不越级声明、不越权硬件操作和不阻断独立开发的辅助边界。正式时序/CDC/板测未执行就单列NOT_RUN。

### SKL-002：可配置的PYNQ数据通路验证

唯一活动目标：`skill/pynq-overlay-dma-validation/`。A负责开发与真实板级准入，C负责独立复核，复用B已批准的golden和故障输入；必要时由B协助专业检查。任何人都不代签未执行的实板测试。

完整包至少包含：SKILL.md、竞赛README、profile/会话合同及例子、可运行检查器与测试、板级操作单、源数据/输出/golden及证据报告、失败/修正轨迹、迁移说明、许可/版本与复核入口。把平台配置、实际驱动适配器、验证核心分开；不把SoundSight的板名、通道数或寄存器地址写死。

本队主打贡献：**面向真实接收链的故障诊断与安全收尾**，辅以精确golden比对。重点验证缓存新旧数据、超时/部分启动后缓冲区归属、停止未确认时不释放、错误profile拒绝、整数比较不因浮点转换误PASS。可复用已有离线实现，不为亮点扩做SG/cyclic/中断全功能或通用新IP。

SKL-002独立复核人的最小验收（团队自设）：

1. 在干净环境复跑准确提交中的全部测试；作者65方法/74子测试仅是9/23候选记录，后续按实际清单计数，不以凑数量验收。结构检查不能替代行为测试。
2. 至少两套不同题目/IP/数据格式的profile，在不改验证核心的情况下运行；用普通流处理样例作迁移，不新增四麦声学模拟。模拟第二板只能证明配置迁移，不能称两块板实测。
3. 保留正常S2MM接收及匹配设计才可做的loopback；故障至少覆盖artifact不匹配、长度/地址对齐、缓存陈旧、超时/停止未确认、短输出、golden不符（含大整数）。关键故障不得误PASS，不得不明归属释放DMA内存。
4. 真实PYNQ路线单列：A先核实实际镜像/板支持、同构建bit/HWH、分配器/缓存/实际驱动语义和停止机制，再在已匹配硬件上跑接收/golden/重复运行。使用实际板卡现有工程，不臆造MM2S或有副作用的寄存器访问。
5. 实测报告记录字节数、次数、错误、计时方法、软件开销和实际端到端吞吐/延迟；FPGA资源和时序引用同构建原报告。软件mock耗时不得当硬件加速，Skill优化和PL加速分别比较。

PYNQ若未能准入，继续交可复用离线工具、失败记录和明确未测范围；已有Vitis采集/声学主线照常推进。**这只能验收离线Skill范围，不能声称真实PYNQ项或加分证据已完成**。Vitis/PetaLinux替代不等于PYNQ验证；届时公开登记加分风险，不用假板测补齐。

## 4. 制作流程、交付位置与分工

固定原始失败/合同 → 最小修复及同输入前后测试 → 陌生上下文复用 → 整理可见纠错和贡献 → 推送候选 PR → 非作者真人绑定 SHA 复核 → 按批准范围合入 → 新入口验证及批次收尾。

- A 同时负责两项源码；在同一工作执行任务中串行写入，两项可分别发布和复核，不等齐。
- B 对 #21、C 对 #22 分别负责独立判断。既有 B golden 与批准未失效的不重做；C 与 A/B 同等遵守资质、证据和非作者规则。
- 源码唯一维护在 `skill/`，任务包仅留版本、输入和证据。不能覆盖历史日志、改旧清单使哈希通过，或把本地混合改动整体送审。
- 原专项聊天已删除；依[新聊天提示](chat-start-prompts.md)分配到成员执行/复核任务。不强制每项 Skill 新建聊天或整库副本。
- 提交包保留说明、场景/限制、实际命令/cwd/工具版本、首错与修复结果、日志哈希、许可及待测项；只记工具实际提供的耗时/token，不估填。
- 不交隐藏思维链、凭证或他人未授权录音；不把引用外部团队工作流当作本队原创贡献。
