# 开发过程中的报告支撑资料留存指导

状态：活动指导，2026-10-13 经用户明确授权统一启用。用于后续任务和安全断点接续；不倒填历史验收，不热换在途候选。

2026-10-12按用户采纳决定整理。适用于通用FPGA工程项目的多人开发，与参与人数无关。围绕[项目开发流程](project-development-flow.md)收集后续技术报告、论文、项目汇报及交付说明需要的材料；与[总体任务分配](team-tasks.md)、[工作人员与AI协作](team-workflow.md#human-ai-collaboration)、[Git管理](git-workflow.md)配合。具体承担者和实际操作权限沿原任务确定，本页只规定资料的用途、留存范围和交接要求。

## 1. 留存目标与基本原则

资料应能回答“为什么选这个方案、在什么条件和版本上做了什么、实际得到什么、结论能覆盖哪里”。开发时顺手保存难以补取的事实和已有产出，写报告时从这些材料组织结论，不靠回忆补造测试、数据或历史决策。

- 按报告结论和工程复核需要保留材料，不按失败次数、文件后缀或目录大小一律全留或全删。
- 小型结果、关键条件、版本关系及证据入口常规保存；大型原件按诊断、复核、复现和定量分析用途选择范围；可再生成缓存不默认永久归档。
- 失败以总结为主、必要原件为辅；成功也只在所需范围内留存真实支撑材料，不能只挑成功片段掩盖失败、超时、拒绝或缺失。
- 沿已有Issue/PR、阶段记录和证据索引一次记录、直接引用。小修可挂父任务，批量运行可共用一份记录，不为每次尝试另开报告包或审批。
- 估算、作者自测、独立判断、仿真、实板及正式验收分别说明；`UNKNOWN`、`NOT_RUN`、`UNVERIFIED`保持真实含义。未采集或无法复核的材料不能标成已验证。

## 2. 沿项目全过程收集哪些材料

下表列适用材料及报告用途，不是每个项目都要完成的统一测试清单。已有材料和有效证据直接引用；不适用项不为填表而新增工具、试验或产物。

| 项目阶段 | 随工作保存的主要材料 | 后续能支撑的说明 |
|---|---|---|
| S1 系统需求与验收指标 | 需求来源、适用场景、系统输入输出、指标与单位、测量方法及验收条件；外部资料的标题、版本/日期、出处和引用位置 | 要解决的问题、目标及评价口径；区分设计目标和实测结果 |
| S2 系统建模与总体设计 | 系统架构及接口依据、关键方案比较与选择理由；模型/输入入口、浮点与定点结果、算法/位宽/调度的精度和资源权衡；系统组合预算及向子系统分配的依据 | 总体方案为何可行、预算如何分配、为何采用某种算法或结构 |
| S3 软硬件与子系统开发 | 适用的模块框图、协议时序、状态机、时钟复位/CDC和恢复设计；权威接口定义及派生文档；模型/RTL对齐、自测条件、结果及剩余未知 | 关键设计与实现方法，以及局部结果覆盖范围 |
| S4 持续集成与整机实现 | 实际接合配置、共享资源与接口影响；同候选的层级和全板资源报告、约束/CDC及适用时序报告；有分析价值的布局或优化前后对比 | 完整组合的资源和物理可行性、优化收益及代价 |
| S5 系统联调与最终验收 | 实际板卡与连接/仪器配置、加载身份、软件及运行条件；输入、观测方法、测量数据、ILA/日志和必要照片/演示；适用压力、边界及恢复结果 | 系统实际效果、性能与可靠性；不能由局部演示推定整机通过 |
| S6 项目交付与归档 | 最终准确候选、构建配置、匹配产物和报告、正式验收范围；资料索引、可编辑图源和绘图/计算入口、必要原件及引用来源 | 报告数字与交付版本对应，后续能找到、读取并复核资料 |

### 需要贯穿阶段保留的设计与验证信息

预算保留初始分配、重要变更及其依据、实际结果和差异处理。只比较初始与最终值，不能证明开发全过程一直满足预算。MATLAB等模型的资源估算、综合报告与布局布线后的结果分列，不互相代替；全板统计包含已接入模块、公共互连和调试开销。

模型与定点结果记录输入来源、独立预期、数值格式、缩放/舍入/饱和规则和评价口径。报告涉及误差、精度、吞吐或时延时，保留能重算该项结论的必要输入、输出、脚本和数据；端到端指标不能只引用某个局部模块结果。

框图、时序图和流程图优先保留实际使用的可编辑源及导出图；结构、接口或配置变化后明确适用版本。已有图源或模型在权威源码位置维护，不另外复制成一套活动工程。重要取舍和有价值的故障/优化过程沿原任务简要记录，不规定每项目必须凑若干案例。

OOC、覆盖率、Pblock/SLR布局、眼图、误码率、长稳和高低温材料按真实设计、工具及验收要求收集，不统一要求UVM、覆盖率全满、固定运行时长或温度范围。局部时序估算不能当全板物理收敛；时序结论结合正确约束、适用setup/hold等检查及报告范围判断，不能只展示一个WNS数值。

## 3. 资料如何关联输入、版本和结果

重要结果沿原任务或现有归档索引记录下列适用信息。已有构建清单、批次日志或证据记录足够时直接引用，不重复抄写，也不强制每张截图单独填表。

| 信息 | 最小适用内容 |
|---|---|
| 用途与范围 | 支撑的系统/模块目标、报告结论或指标；实际经过/绕过的链路及限制 |
| 准确候选 | 源码提交或可恢复快照、实际使用的未提交差异/未跟踪输入；需要时引用候选到合入版本的映射 |
| 条件与入口 | 输入/用例或数据批次、关键参数、适用种子；工具、配置、约束、命令或运行入口和测量方法 |
| 结果与状态 | 实际输出、单位、检查/比较口径；新执行、复用、跳过、失败或未测，剩余未知 |
| 资料位置 | 摘要、图表/数据、必要原件及生成入口的稳定路径或链接；重要归档/产物的校验信息 |
| 交接与保留用途 | 原任务中的产出/分析/接收责任入口；大型原件为何保留、何时重新核用途 |

板卡编号、接线、加载产物、软件、实际运行配置和适用身份回读用于实物证据；纯模型或仿真记录不强填板卡编号。未提交候选可以支撑身份准确的开发诊断，但不能写成干净提交的正式验收结果。构建身份与寄存器读回的边界按[Git指导](git-workflow.md#build-identity)处理，短Git哈希、日期或Dirty标志不能单独证明整份运行逻辑匹配。

身份或条件缺失时，注明缺口，限制依赖它的结论并按用途处理；不是把整份材料一概宣布无效或删除。沿用旧证据先核输入、假设、配置和版本仍适用；新结果不倒填旧报告。

## 4. 多人如何随工保存和交接

资料产出随工程任务交付，不另设固定成员或所有数据都经过的中转岗位。任务形成时，明确本批关键指标需要哪些现成材料、哪些难以重取的观测需要在运行时保存，以及结果直接交哪个后续环节；小补丁沿父任务轻量记录。

执行环节保存当时条件、准确输入/候选、实际结果及必要原件入口。分析环节保留数据处理、筛选/转换和作图方法，将派生图表关联原数据及其适用范围。报告整理环节建立结论与资料的对应，查找缺口并回原责任环节确认；不能自行补造工况或把推测改成事实。重要结果的技术判断沿既有模块/系统复核完成，不额外增加“资料签收批准”关卡。

工作人员与AI按[协作指导](team-workflow.md#human-ai-collaboration)开展整理、索引、计算、作图和检查。AI生成的方案图、解释或检查结果注明来源和实际验证程度，不能当作现场照片、仪器读数或真实执行记录；AI写成的成功摘要不能代替原有验收证据。

交接时一次给出可用入口、对应版本/配置、实际结论、未测及必要原件的位置；现场数据直接给分析环节，工程问题直接给相关实现环节。没有实测、文件读回或接续确认就如实记录，不把上传、发送或打包当成已读、已接收或已验收。

## 5. 按用途管理不同文件

| 文件类别 | 默认保存方式 | 大型或特殊情况 |
|---|---|---|
| 源码、TB、模型、脚本、约束、输入及必要依赖 | 保持一份权威维护源，以准确版本/冻结输入入口关联结果 | 不为每次运行复制完整源树；仅提交SHA而实际依赖已丢失不算可复现 |
| 用例结果、检查摘要、必要日志、测量/计算数据 | 保存足以说明条件、实际结果并复核报告结论的部分；已有批次记录直接复用 | 巨量文本可提取关键记录或机器可读结果；提取方法与原件用途明确，不能过滤掉相关失败事实 |
| 图表、照片、演示和截图 | 重要图表保存可编辑源/数据/作图入口及清晰导出，照片/演示保存必要场景说明 | 保存能说明判据的片段，不无限录制；标清筛选或裁剪范围，不借裁剪掩盖异常 |
| WDB/VCD/FSDB等波形数据库 | 按观察需要选择信号、窗口和精度，不默认保存完整全层级全时长数据库 | 必要时保留完整数据库，并记录用途、工具和读取依赖；已保留文件应能按所给入口读取 |
| 波形显示配置，如WCFG | 有复用价值时保存，可按工程用途纳入版本管理 | 它描述显示信号/顺序/格式等，不是大型采样数据库，不与WDB等一概排除 |
| 编译/展开数据库、缓存和整个运行目录 | 按运行、复用和调试需要临时保存，不默认作为报告永久附件 | 若读取波形、特定复现或工程交付确需其中依赖，则保留相应必要部分 |
| 正式工程包、加载产物和匹配报告 | 按准确候选与构建清单关联必要产物及校验信息 | 阶段完整工程交付仍按项目要求执行；本页不以“缓存”名义删掉必要工程/IP/平台依赖 |

截图适合呈现局部现象，不能一律代替需要展开信号、重新计算或独立复核的原数据。报告正文可以只放清晰图表和证据索引，必要原件另在受控位置保存，不要求把完整运行目录都塞进报告附件。

## 6. 大型仿真文件的采集与保留

先决定要验证的行为、关键输入、判断方法及必需观测，再选择记录方式。已有有效结果复用；不为了资料齐全重复仿真，也不为每次运行自动全量转储。

当用例能可靠复现且检查器有效时，可先运行不记录波形或有限记录的批次，以输出比较、断言和结果摘要判断；失败后在相同准确候选、输入、配置和必要环境下有针对性重跑。随机种子只是条件之一，不能单靠相同种子保证相同现场。工具正常退出不等于功能通过，未生效的断言或检查器也不能作为通过依据。

对难以复现、一次运行成本很高或事后难以再取得的事件，提前保留必要观测、输入/输出和触发信息；可选有限持续记录或工具实际支持并已验证的历史缓冲，不强制全部采用“失败后重跑”。需要故障前信号时，须提前记录、使用真实可用的历史缓冲，或重跑并从更早时刻开始；错误发生后才开启记录，不能凭空得到之前的波形。[AMD波形记录说明](https://docs.amd.com/r/2023.1-English/ug900-vivado-logic-simulation/Using-the-log_wave-Tcl-Command)

记录范围按诊断需要选择外部接口、握手、状态机、计数器、FIFO指针/占用和其他相关内部信号。默认避免把大容量RAM/FIFO内容全量转储，必要时保留选定地址、样本或状态；不能统一禁止内部信号、存储内容或复位/训练阶段，因为它们可能正是故障原因。采样窗口、时间分辨率及输出大小兼顾所需精度和存储成本。

使用当前仿真器和版本支持的记录方式，不把某个`$dumpvars`、`$dumpon/$dumpoff`示例作为所有工具的通用脚本。首次设置或实质变更后确认真正记录到所需信号和窗口；波形图保留信号名、时间尺度、数值显示/单位及对应输入说明。WCFG与波形数据库分开管理，其显示配置用途见[AMD同一说明](https://docs.amd.com/r/2023.1-English/ug900-vivado-logic-simulation/Using-the-log_wave-Tcl-Command)。

## 7. 反复失败怎样留存

失败次数不决定完整现场的留存数量。采用[总结为主、必要原件为辅](git-workflow.md#failure-retention)：在原任务或已有批次记录中说明输入、准确版本/配置、实际异常、主要处置、复验和剩余未知，不要求每次失败都封存完整工程、运行目录、波形或现场录像。

相同条件下重复出现的同一问题可以合并总结，保留次数、适用条件和统计口径；版本、输入、参数、失效现象或处置有重要变化时，分组说明这些差异与结果。工具/环境失败与产品行为失败区分，不为了归档重新制造每一次完整现场。

必要原件按用途选择：仍需诊断、难以再次取得，或用于定量复核/验收时，保存相应输入、日志、波形或样本的最小充分范围。它可能涉及一部分、全部或不涉及历次失败的原件，不能机械规定只留首次/末次，也不默认全量留存。尚未确认诊断信息足够时，不先丢弃唯一现场。

问题已解决、总结足以复盘且原件无后续用途时，不要求永久保存完整失败现场。对代表性现象可以留截图/片段及解释；涉及成功率、误差分布、丢包或稳定性统计，仍需保存能复算该项结论的必要数据和失败/超时/缺失口径，不以选出的案例替代统计样本。

开发中改过版本或参数后的反复试错，是过程历史，不能直接当作最终固定配置的成功率；最终验收候选按自己的实际测试条件、样本与结果判断。这里规定资料留存，不改变[自动返修停止和接续边界](team-workflow.md#human-ai-collaboration)，也不据此授权增加自动返修轮次。

## 8. 存放、归档与清理

沿项目既有权威源和材料位置组织资料；当前源码/TB/模型/输入按现有活动目录维护，历史冻结材料不倒填。不要为报告另起`doc/assets/`等目录去复制一套活动源。必要的报告图表和证据索引可在原交付/归档位置组织，通过准确版本与入口关联源数据。

目录或批次标识能唯一对应任务、候选/配置及运行时，工具原始文件名可以保留，不强制每个文件名都塞入短SHA。避免无条件上下文的散落文件；重要文件/归档用实际校验信息确认完整性。共享可写目录同时一名写入方，不归档仍在变化的数据库；交接核所需材料已可读取，关键材料不能只存在临时本机绝对路径或即将过期的链接。

大型文件是否进入Git按维护、分发和体积判断，可用项目认可的受控存储保存并在索引给稳定入口及必要校验；不能只因Git忽略就认为已经归档或可以删除。更改忽略策略或迁移材料须先完成实际输入、保留用途及引用检查；不能靠忽略掩盖成果。

临时CI产物的保留期按诊断、复核、交接和归档节点确定，不统一设若干天后自动删除，也不只上传失败产物。需要支撑最终成功、前后对比或验收的结果同样保存；长期必要材料在临时产物过期前转入可访问的受控归档。平台产物和保留配置依实际工具处理，GitHub Actions参考[GitHub产物文档](https://docs.github.com/en/actions/tutorials/store-and-share-data)，不把其他CI平台的配置直接套用；这里不声称已部署自动归档或清理。

大型原件在问题结清、相关复核完成或阶段归档时重新核用途及读取依赖。清理按[文件与工作区规则](generated-artifacts.md)进行：先确认总结/必要数据已保存、无待诊断/待审依赖、无独有成果遗漏，并核有效授权、精确路径、链接和占用。可再生成不代表可不加检查直接删除；已无用途的完整失败现场也不为清理而强制再备份全量副本。

## 9. 写报告和阶段交付时如何使用

把主要结论、指标和图表关联到现有证据及其准确候选、条件和范围；沿[阶段收尾](phase-closeout.md)保存最小索引，不另建一套任务状态数据库。重要量化结果应能从图表追到数据和计算方法，关键方案说明能找到当时依据。

写作检查重点是：目标与结果是否分开，单位/坐标/样本和分母是否清楚，优化前后是否按可比条件比较，模型/仿真/实板是否分列，资源/时序报告是否覆盖所声明的完整配置，异常及未测边界是否保留。实际最大观测值不能写成已证明上界；局部PASS、演示视频、打包或合并不能替代整机验收。
