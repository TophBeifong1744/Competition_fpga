# FPGA项目总体任务分配指导

状态：活动指导，2026-10-13 经用户明确授权统一启用。用于后续任务和安全断点接续；不倒填历史验收，不热换在途候选。

2026-10-12按用户采纳决定更新。本页面向整个FPGA工程项目，先确定阶段目标、工程成果、任务及依赖，再配置责任和执行资源；不预设人数、固定专业岗位或现有成员分工。配合[项目开发流程](project-development-flow.md)、[模块实施方法](module-development-flow.md)、[团队工作流](team-workflow.md)及[Git管理流程](git-workflow.md)使用。

本文是通用任务分配指导，不是人员派单或另一套状态台账。具体承担者、有效操作授权及在途任务以[项目约定](../AGENTS.md)、[配置](../team-workflow.yaml)和原Issue/PR为准；本次重排在原Issue落实，不打断在途工作；指导不直接授权任何实物动作。旧人员表不作为新任务结构的前提，历史分配可从Git版本及[历史入口](../archive/2026-09-23-before-team-workflow/README.md)追溯。

重新组织以任务成果、关键路径、能力、工作量、验证独立性及操作权限决定人员和AI配置，不默认继承旧分工或聊天。历史指导用于复盘踩坑，直接交接、不重复派工/构建/复核、单写入方及真实证据的教训保留；仍适用成果复用，实际重排明确任务和工程交接。人机实施方式见[工作人员与AI协作指导](team-workflow.md#human-ai-collaboration)。

## 1. 分配主线和任务边界

总体分配沿“项目目标与验收 → 项目阶段 → 工程成果 → 任务包 → 接口和依赖 → 指标与验证 → 交接和结果责任”展开。流程决定要完成哪些工作，技术架构决定拆分边界，依赖决定推进顺序；人员安排在任务结构明确后确定，不改变必要技术产出和验收条件。

任务首先按功能、子系统、接口及可验证成果划分。时钟域、复位、共享资源和物理布局进入设计及接合条件，但不强制将任务边界等同于Bank、Clock Region或Pblock；控制面与数据面可以分别设计，通过明确协议、配置及数据所有权共同接合，不能据此省略交叉验证。

任务粒度应能交出有意义的设计结论、可用模块或可测链路。既不按每个函数、截图或小修独立开包，也不把整个工程交成没有中间判据的大包。已有合同、模型和有效结果直接引用，普通小修合批。

## 2. 必须覆盖的任务及责任

下表是任务类型和结果责任的覆盖清单，不是固定岗位、人数配置或实际派单；按项目适用内容取用。一个责任类型可贯穿多个阶段，多种责任可结合承担，但重要模块/阶段的独立复核不能由参与实现或实质修改验收资产者自签。

| 任务类型 | 应明确的工程成果和结果责任 |
|---|---|
| 系统需求与验收 | 系统边界、适用场景、指标、真值及测量方法、异常和恢复条件；维护要求与验证的对应 |
| 系统建模与总体设计 | 端到端算法/数制与实现方案、组合可行性、指标预算分配及变更依据；跟踪后续实际结果的校正 |
| 共享平台与基础设施 | 时钟复位、IO、地址空间、互连、存储/带宽、IRQ/DMA及必要观测的权威定义、约束和接合支持 |
| 子系统/模块实现 | 设计、RTL或适用软件、必要作者自测、约束与配置、适用局部资源/时序信息及可用候选；不能只交代码 |
| 接口接合 | 两端就绪条件、格式/时序/配置兼容、所有权、接合用例和结果；接口说明不能代替实际接合 |
| 集成、构建与物理实现 | 准确组合候选、实际输入和工作区、全板资源/约束/时序及匹配产物；分清接入、构建执行和整体技术结果责任 |
| 验证、现场与结果分析 | 从需求独立确定预期；适用功能、协议、数值和系统验证；现场状态与操作、真实数据分析及限制分别明确 |
| 工程交付与发布 | 完整可用工程、适用模型/依赖/数据、匹配产物、身份及使用恢复说明；交付核对、验收判断与发布授权分别明确 |
| 项目协调与变更 | 任务和依赖、接合节点、工作区/板卡冲突、关键选择及例外处理；协调不成为额外加工或批准前置 |

可用RACI说明责任：R负责执行，A对约定结果负责，C提供必要协作，I接收相关信息；这些字母不对应任何现有成员。每个明确交付物有一个清楚的最终结果责任入口，执行可协作；不同交付物分行记录，不把多个任务混成一行制造责任歧义。不强制逐任务填写完整矩阵，也不为普通小修增加表单。

RACI中的A不自动获得技术取舍、独立复核、合并、验收或发布权限，也不表示每个动作都须审批。重要结果的合格非作者判断按原授权和准确范围执行；适用成员指定AI代表接受的规则仍按项目约定，不虚构平台批准或无归属代签。

## 3. 沿项目六阶段分配工作

### S1 系统需求与验收指标

先分配需求澄清和验收设计任务：确定项目用途、系统边界、外部输入输出、正常/异常及停止恢复行为；明确功能、精度、吞吐、端到端延迟、持续运行和适用安全/环境要求。输出可检查的需求及测试条件，标明本轮范围、后续目标和必要未知。

本阶段提出资源和实现约束、初步预算及待验证假设；具体算法、地址/引脚及物理区域设计在S2依据方案形成，不在可行性分析前全部锁死。验收规划从这里开始，不到板测时才补判据。

### S2 系统建模与总体设计

分配端到端建模、总体架构、共享平台、接口和指标分配任务。数值链优先用MATLAB或现有等效浮点/定点模型，联合比较算法、精度、数制、调度、缓存和硬件成本；控制路径分析状态机、协议、所有权及故障恢复。模型结果、估算、实际综合/实现和板测结论分开。

形成系统到子系统/模块的适用指标，包括各类逻辑/存储/计算资源、时钟与IO、有效共享带宽、缓存、延迟和精度，计入公共底座、接合及调试开销。明确预算依据、硬上限、估算不确定性、余量、检查方法和结果责任；超限先优化或提出有依据的重分配，不能默认容许再超10%或直接把上限改成实耗。

同时分配权威接口定义及配套更新、软件提前验证、必要观测和构建身份任务。共享时钟、地址、引脚和仲裁的变更须核上下游及整机影响；统一管理不等于所有工作由一个永久岗位独占。SystemRDL、SystemC、Pblock等按真实需要选用，不以工具名称作为完成条件。

### S3 软硬件与子系统开发

依据已明确的目标、指标和接口分配平台、子系统、适用软件、测试及接合任务，按真实依赖并行推进。每批实现包含必要设计、自测、约束/配置和交付；作者不能把基本正确性与明显缺陷全部留给后续验证或构建方。

数值实现按独立定点参考核适用输入及边界；bit-exact表示位一致，有容差时单独定义误差规则，不将“误差不超过1 LSB”称严格位一致。控制、接口及恢复按事务预期检查，不强制数值模型或UVM。独立验证任务保留，不能仅因作者自测通过就推定参考和系统目标正确。

局部资源/时序检查按变化及适用约束安排，不统一要求所有任务先完成OOC才接入；OOC综合时序非负不能代表完整物理收敛。软件可用模拟后端、最小测试壳或环回提前排错，实际缓存一致性、IRQ/DMA和物理行为仍须真实接合验证。必要自测后可用端点直接交下一接合/集成责任环节，不等全部子系统齐全。

### S4 持续集成与整机实现

按重要增量分配接入、组合验证、构建和物理实现任务，明确本批准确输入、接合对象、执行人、工作区和输出。权威集成基线统一，执行人按具体任务指定；可以有目的地隔离构建或独立复现，不同时写同一工作区/EDA输出，也不无目的重复有效同候选run。

核组合行为、接口及配置、共享资源/并行干扰、完整同候选层级与全板资源、约束覆盖、CDC/RDC/DRC及适用布局布线后setup/hold。OOC模块和公共实例须完整计入，黑盒缺项不是余量。分层检查按成本与风险安排；模板、脚本或CI配置存在不表示检查已执行。

接入后超限或方案不成立，结果责任环节组织相关设计任务调整；不能只让构建执行人兜底，也不能继续叠加已知不可行功能。规划或复用必要ILA、输入及判据，第一条独立可测链路满足必要时序/安全条件后安排有界上板，S3～S5交错推进。

### S5 系统联调与最终验收

分别明确现场操作、刺激与环境准备、观测、结果分析、故障修复及整机判断责任。核实际加载产物/软件/配置及适用身份；先完成当前范围的输入、处理、输出和停止/重启闭环，再按冻结场景核整机指标、并发负载及适用恢复和环境条件。

记录真实输入/真值、板卡和环境、样本数/时长、成功/错误/拒绝/超时/缺失，以及准确候选和未测范围。数据直接交分析环节，工程问题交相应实现环节，现场事实由现场环节补充；分析结果不自动授权下一次实物动作。

限定模块、模型、仿真或板测结论只支持对应范围；最终验收依完整系统完成标准判断，不以任务数量、构建成功或几个模块分别通过替代。不统一规定覆盖率、72小时或高低温压测，必要工况来自真实场景、风险及交付要求。

### S6 项目交付与归档

分配工程收拢、依赖与匹配核对、使用/恢复说明、验收判断、发布执行及必要复盘任务。交付完整可搬移工程及必要源/IP/BD/约束、适用软件平台/依赖、模型/数据和匹配产物；仅适用时提供MCS、DCP等，不强制所有项目使用相同产物清单。

源码/快照、实际配置/工具/构建身份、产物哈希及真实报告对应；核完整性，真正打开/运行过才声明相应能力，不为包装重复构建。交付执行、准确范围接受、正式验收和发布权限分别核实；合并不自动关闭未完成系统任务。失败留档按[总结为主、必要原件为辅](git-workflow.md#failure-retention)，复盘用于改进规则，不强制为每次小修开会或造报告包。

## 4. 任务包、依赖及交接记录

沿原Issue/PR或已有合同记录任务，不建第二套手工状态数据库。子系统/模块可用[任务模板](templates/module-work-package.md)，其他任务沿同样原则简述适用内容；已有输入、预算和有效结果直接引用。

任务记录按变更影响和风险取用，不按代码行数分级，也不增加固定标签或审批链：

- 主任务包：新功能、架构调整或重要增量，明确所支撑系统目标和阶段、范围、准确输入、适用指标与完成条件、允许动作及保护项、必要验证及结果入口、真实依赖、执行及最终结果责任、下一接收环节。已有合同和未变内容直接引用，不要求重复全量填表。
- 补丁/维护：既定范围内的小修挂在原Issue/PR下，继承父任务的目标、接口、预算、完成条件、责任和有效授权；只补充父任务引用、准确候选及实际差异、变更点、影响范围、实际自测及未测项。上述约定变化时明确补充，不能因轻量记录而省略受影响的验证或扩大权限。

小改动若影响关键时钟/复位/CDC、公共接口、精度或指标分配、停止恢复及实物安全等，按实际影响补设计和检查，必要时更新原任务范围；例如三行分频修改不能仅凭行数认定为普通低风险补丁。适用时注明非作者判断、接口接合、构建、现场操作和分析责任，责任与权限清楚即可，不强制每个任务配四个人、完整RACI或四道审批。重要结果的独立判断仍按第7节执行。

交接同时给出可用入口、准确候选/配置、实际结果、未测和剩余问题，以及写入/板卡占用的交接状态。节点阶段交完整可用工程，原工程返修可沿准确增量交接，不为小步骤反复全量封包。收到可用材料即按接口接入，不将协调核收、另行加工、重复复核或状态更新变成必要开工前置。

依赖必须是具体输入、接口、配置、资源或安全条件。一次说明真实缺件和影响，只暂停受影响路径；其他独立任务继续。不重复派发在途工作，不把某一确认节奏施加全项目，不以“全阶段材料尚未齐全”为由等待可测链路。

## 5. 集成、构建和现场责任边界

系统组合技术结果、模块实现、接合验证、构建执行、现场操作、数据分析、独立判断及发布授权分别说明，不能因其中一个责任被指定就推定其他权限。总工程统一指权威组合入口及可追溯候选，不指一个成员永久独占所有构建或现场工作。

同一可写checkout/EDA数据库/输出目录保持单写入方。并行任务使用受控隔离目录及明确输入，复用有效结果；计算预算按现有规则共享，不抢占、中断或制造无效任务。仅因读取固定提交不创建完整副本。

下载、复位、接线及会改变板上状态的在线调试按现场有效授权排他执行；协同观察和分析可以并行。记录板卡、加载身份、操作人、占用/交接和释放，预计结束时间不表示自动接管。构建或分析完成不自动授权下载、运动或其他实物动作。

### 探索板测的改动、产物及结论边界

有界上板限定测试范围、条件和判据，不表示一定使用临时工程；正式实现中的首条可测链路可沿现有任务直接验证，不为每次上板新建分支、完整副本或审批。需要临时Bypass、强制信号或测试刺激等探索改动时，明确本批探索范围、接合/构建及现场责任，通过任务分支或明确实验配置与正式行为分开。

版本隔离不能代替工作区和EDA输出隔离。真实并行写入/构建时使用受控独立工作区及输出；既有工作区单写入且无冲突时可复用，不在脏目录或运行中切换配置/分支。记录准确候选、实际未提交差异（如有）、实验配置、临时改动及加载产物，使结果对应实际被测工程；具体操作沿[Git指导](git-workflow.md)执行。

结果交接须说明实际经过及绕过的模块、替代输入、观测与判据，以及结论能支持和不能覆盖的范围。探索结果可以支持对应范围的后续推进；Bypass下游可用不证明被绕过模块或正式端到端链路通过，撤除Bypass或改变配置后补受影响的验证，原结论不倒填成正式配置通过。

探索改动拟合入集成基线时，明确哪些撤除、哪些转为正式设计，核接口、默认行为及资源/时序影响，沿既有PR和适用独立判断完成相称检查，不另建“探索转正式”审批关卡。正式需要的ILA、状态寄存器或可维护调试配置可按明确用途纳入基线，并计入预算；保留原候选/配置证据及其限制，关联正式候选与新增或仍适用的结果。必要时更新下一接收任务及验证范围，不将全部探索补丁或调试产物直接充当正式交付。

## 6. 跨模块问题和回归决策

先明确本问题的诊断与结果责任，沿接口、预算、配置和实际观测收集最小必要事实；相关实现、平台及现场环节协同，依据根因确定修复和复验范围。不要先按专业标签判责，也不将报警位置当成已经确认的根因。

- 边界时序：核时钟/约束、发送和接收路径、扇出、布局布线及接口时延预算；两端寄存不能自动证明顶层过失。不统一强制所有非总线输出打一拍；增流水级须核握手、数据对齐、时延及系统影响。
- 共享带宽/溢出：核实际访问、突发、排队、仲裁、缓存和软件服务是否符合约定，以及原预算是否成立；不以突发小于16等统一阈值自动判某类模块整改。可能需要修改模块、共享平台或整体方案。
- 挂死/恢复：超时监视、状态计数和ILA提供定位线索；结合完整事务、下游反压、复位及buffer/DMA/软件所有权查根因。按协议收尾或已设计的隔离/协调恢复执行，不凭监视器编号直接认定责任或擅自局部复位。

板上已发现的故障返修沿项目授权优先回板：必要修复后本次跳过仿真，保留新产物必需构建、受影响时序/CDC和安全检查，复用原复现输入及观察点；不将补仿真作为回板前置，也不自动跳过新功能关键验证。

后续验证按复现性、影响、已有覆盖和建模成本选择。重要且容易复发的可仿真缺陷需有能检出错误的定向回归，已有有效用例可复用；物理/环境问题保存可重复板测条件和判据，按相关变化及验收风险复测；样机/工装问题完成处置或隔离并确认影响后结清，不因“非RTL”自动关闭。真正剩余缺口沿原Issue记录责任和实际需要的节点，不为每次跳过仿真统一新增技术债、封板期限或全发布复测。

## 7. 完成、独立判断和变更

作者完成必要自测即可交可用候选；重要模块或整机阶段结合接入结果做合格非作者判断，小修自检后合批。参与实现或实质修改验收资产者不能把同一结果称为独立批准；多个模型意见或角色切换也不代替有效归属和范围。

实现完成、模块交付、接入通过、整机验收和正式发布按各自完成条件判断，不能互相替代。检查缺失、旧报告不适用、身份不符或工具失败如实记录；UNKNOWN、NOT_RUN、UNVERIFIED不改写PASS。首次判断覆盖本批申请范围，返修集中说明差异，只补受影响检查并复用仍适用结果。

关键方案、公共接口、指标分配和硬件/工具选择变更按原权限确认，说明上下游及整机影响；普通等价修复和未变选择连续实施。无进展返回根因或总体设计，不通过改阈值、改golden或更换任务名消除失败，保留原累计停止规则。

## 8. 当前工程衔接和指导范围

新分配先检查任务类型是否遗漏，尤其是系统组合指标、接口接合、真实结果分析及独立判断；再安排承担者及协作。保留结果直接交下一责任环节、整批推进、小修合批、集中非作者判断和工作区单写入的教训，不把旧人员布局当作通用原则。

各类指导重构完成并确定衔接安排后，现有工程在安全断点接续已明确任务及有效证据，不重新从S1全套开工。实际成员重排在原任务和有效配置记录交接；实际转派、安装和发布沿本轮有效授权和原任务接续，不新增产品或实物操作权限，不代签，不更改验收目标、日期、产品或实物权限。Git版本、候选映射、构建身份和留档的具体操作引用Git指导，本页只明确相应任务及责任。
