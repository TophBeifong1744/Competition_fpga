# Git与GitHub管理流程

状态：活动指导，2026-10-13 经用户明确授权统一启用。用于后续任务和安全断点接续；不倒填历史验收，不热换在途候选。

2026-10-12按用户采纳决定更新。适用于整个项目，与参与人数无关；与[项目开发流程](project-development-flow.md)、[团队工作流](team-workflow.md)及[项目授权](../AGENTS.md)配合执行，任务入口见[配置](../team-workflow.yaml)。本页规定Git版本、候选、构建记录、发布及留档管理；具体成员分工和工程/实物操作权限由原任务及有效授权确定，不在本页指定A/B/C职责，不另建任务状态数据库。

重新组织时，Git服务于新的工程任务及协作安排，不以旧人员、分支数量、聊天或固定合并/构建执行人规定分工。沿新任务明确准确输入、写入方、复核范围及有效Git权限；保留版本追溯、共享工程单写入、相称验证和总结留档的教训，不复制旧审批层次。人机职责见[协作指导](team-workflow.md#human-ai-collaboration)，本页不代替任务分配或实物授权。

## 1. 任务、分支与版本的含义

Git管理文件版本与组合历史，GitHub承载Milestone/Issue、PR、批准和发布记录。任务完成以约定完成标准和实际证据为准，不能用commit、merge或Tag代替技术验收。

| 对象 | 用途与边界 |
|---|---|
| Milestone / Issue | 项目节点、工作包目标、负责人、依赖、完成标准及交接；无代码的数据交付可直接使用Issue |
| main | 唯一集成基线，持续接入已获准确范围认可的变化；不表示每个提交都已完成全部板测或整机验收 |
| codex/<issue>-<slug> | 新任务的短分支；旧返修留原PR、分支和问题ID，不因换聊天重置问题历史 |
| 发布候选 | 在需要冻结时固定准确SHA与配置；只有确需与下一轮开发并行时才增加短期release分支 |
| 正式Tag / Release | 标记已获发布授权的准确版本，保存产物与验收范围；未满足项目验收的候选必须明确标为测试/预发布 |

当前不增设永久develop分支。分支数量由隔离与并行需要决定，不由FPGA规模或团队人数决定。

## 2. 开工前确认工作区和基线

先读项目入口与当前Issue/PR，明确本批目标、修改范围、负责人、接口和下一交接对象。核本地分支、HEAD、未提交/未跟踪/ignored材料、正在运行的EDA任务，以及本地main、origin/main和实时远端main的关系；origin/main只是最近一次获取的本地缓存。

默认每人一个活动checkout，每个可写checkout和EDA输出同时只有一名写入方。脏目录或构建运行中不切分支、不拉取覆盖；只读审查固定提交不另建副本，独立复现或真实并行写入时才创建最小worktree。基线落后时先明确待保留材料及同步范围，再在安全工作区同步，不盲合历史分支。

<a id="workspace-records"></a>
### 工作区、构建与板测记录

在触发接入或构建的原Issue/PR中记录本批实际集成/构建执行人（可用Integrator/Builder字段）、准确候选、工作区、输出位置及下一交接入口；已有任务记录足够时直接引用，不另设认领或收件审批。字段记录实际执行者，不据此指定成员长期分工或推定新增操作授权。

隔离工作区和输出目录须能对应任务及实际run，不强制统一目录名。不同成员可在独立机器/目录构建权威集成基线的明确候选；同一可写checkout、EDA数据库或输出目录不同时交给多人写入，也不沿用仍被占用的临时输出。不为每个小步骤复制完整工程，可信同候选run可复用；独立复现或有明确目的的并行构建保留各自准确配置和结果。

板测记录注明板卡标识、实际加载候选、操作者、占用/交接及释放情况；预计结束时间只用于协调，不意味着到点自动接管。下载、复位和会改变板上状态的在线调试遵守当前现场授权与排他操作安排，其他成员可协同观察和分析。记录沿原任务保存，不增设另一套看板或审批；Git操作许可不等于实物操作许可。

工作区是正在编辑的文件，暂存区是下一次commit选入的准确内容，commit是本地版本检查点，push才把该提交发布到远端。不要把其他人的脏修改顺带暂存或提交；不以reset、clean、stash或强推处理共享脏目录。

## 3. 管理必要输入，分开中间输出与交付产物

Git管理RTL/软件/模型/测试、XDC、IP配置或生成配方、BD描述或生成配方、源清单、初始化数据、构建脚本和必要工程描述。按真实入口保留.xpr、.bd、.xci、Vitis配置等，不采用所有工程必须纯文本的禁令；可再生成的缓存、运行数据库和临时输出按用途忽略。

构建入口明确源路径、器件、实际工具/IP版本、外部依赖、宏、参数和约束；IP/BD生成不得为规避版本记录默认删除IP版本。版本差异先准确记录，是否可用由真实打开、构建或适用兼容依据判断，不预设所有人版本必须相同。厂商生成物由正式工具生成，不手改。

脚本重建与完整可打开工程交付并存：节点交付提供包含必要源/IP/BD/约束/平台/BSP等的可搬移ZIP。脚本存在不证明能重建，ZIP或哈希存在不证明工程能打开；相应结论只由实际执行支持。

需随源码演进的大文件可按需要使用Git LFS，但须确认接收者能取得实际对象。大波形、加载产物和报告可放持久发布/证据位置，以清单记录路径与哈希。GitHub Actions临时artifact有保留期限，不能作为唯一长期归档；.gitignore和LFS指针都不代表原件已交付。

<a id="staged-engineering-changes"></a>
### 工程文件差异与准确暂存

提交前审查.xpr、.bd及相关配置的实际差异，区分会改变工程的有效修改与无关状态。源/约束引用、顶层与器件、IP参数、端口与连接、时钟及综合/实现策略等有效修改和配套文件必须完整保留；绝对路径可能是实际依赖，不能仅因路径属于本机就删除。迁移或交付路径问题通过正式工具及受控工程入口处理，不手改厂商内容。

布局、窗口等经确认不影响工程的状态变化可按需要减少；无害生成字段也可随必要工程变化保留，不强制逐行剔除。避免整文件撤销和盲目全量提交；尤其不能用git checkout -- <file>代替取消暂存，该命令会恢复工作区内容，可能丢失有效未暂存修改。

git add -p或编辑器行/块暂存是可选方法。暂存后检查git diff --cached及配套文件，确保语法、结构和依赖完整，并核对暂存候选与实际被测输入：部分暂存可能形成不同于已测试工作区的新组合。有影响验证结论的差异补相称检查，无关状态差异按依据说明，不为其重复全套构建。

不默认配置clean filter用正则删改厂商工程结构；确需工具辅助时优先采用只读差异展示（如适用textconv）。展示摘要不替代实际提交内容审查；滤镜或导出方法只有确认不丢必要信息、工程能按对应方法使用后才采用。

## 4. 实现、自测与检查点

沿批准目标完成一批有意义的变化，稳定检查点commit，提交说明解释实际行为与关联Issue。临时ILA、诊断参数和实验可用短分支或明确debug配置隔离；确有正式观察需要的调试逻辑可入main，并计资源与时序影响。debug与发布配置必须可区分，不能把调试版本的结果直接套到另一配置。

选择与变化相称的检查，复用未变且仍适用的结果。首次运行、综合/实现、集成/上板及实物动作按项目授权由人操作；板上已发现的具体故障返修跳过仿真，优先按原复现输入回板，保留新产物必需构建、受影响时序/CDC和安全检查。新功能关键验证仍按目标执行。

输入、输出、配置及实际候选必须对应；未执行写NOT_RUN，工具/入口不明确写UNVERIFIED，未知写UNKNOWN。检查器或环境失败与产品失败分开说明，不能用退出码0或PASS字样掩盖漏测、失败和陈旧报告。

<a id="regression-decision"></a>
### 跳过仿真后的回归记录

板上返修优先回板的规则保持；是否补回归根据复现性、复发影响、已有覆盖和建模成本决定，不把每次跳过仿真自动登记为未结技术债。沿原问题简述选择及依据；确有后续验证缺口时写负责人和实际需要完成的节点，不统一规定半天、下一里程碑封板或补仿真后才能结清。

| 情况 | Git任务中应记录的动作与边界 |
|---|---|
| 重要、可仿真且容易复发的逻辑/协议缺陷 | 确保有能检出该错误的定向回归；已有有效用例足够则复用，否则补必要刺激与独立检查。不能把改golden迎合错误实现当修复 |
| 物理/环境问题，仿真建模成本过高或不适用 | 保存可重复的板测条件、触发步骤、观察与判据；以后是否重跑由相关硬件/配置/条件变化及验收风险决定，不对所有大版本一律重复 |
| 外部工装、接线或样机问题 | 记录排查依据、处置/隔离及复验；确认影响与结果后按完成标准结清，不能仅凭“非RTL问题”关闭。未定位仍记UNKNOWN |

分类用于选择验证方法，不代替修复结果、实际安全或最终验收。普通小修并入已有记录；必要用例、板测步骤和后续缺口由原Issue/PR关联，不新增重复报告、固定标签或审批链。

## 5. 提交PR和准确候选

正式交审push准确SHA，并在原PR说明目标、最终变化、接口/兼容影响、实际检查及结果、复用项、未测项和交接入口；报告注明候选、器件、工具、配置、约束及综合/实现/板测阶段。无代码的数据交付不造空PR，普通小修合批，不逐函数开包或重复报告。

复核重要模块时先由目标和父接口独立列预期，再看实现与证据。作者自检可以表达作者认可；合格非作者成员或其指定AI对准确候选的明确同意代表独立接受，登记成员归属、范围和限制。作者切换角色或无归属模型意见不能代签。普通AI评论不自动等同GitHub原生Approve事件，不虚构平台批准。

审批后若有影响已审结论的变化，说明差异并补受影响检查，由原非作者对变化部分重新确认；未变部分直接复用。小修并入重要模块/阶段的集中判断，不对每次push增设独立签字链。

<a id="version-mapping"></a>
### 统一候选与合入版本映射

重要交审/发布候选沿现有PR或构建清单保存一份权威追溯记录，其他位置引用其入口，不要求PR、提交消息和Issue重复维护完整副本。核心字段采用下列名称；已有清单字段可明确对应，不为迁移格式改写冻结原件。普通无构建变化的小修可复用适用配置与记录，不适用项说明原因。

| 字段 | 记录内容 |
|---|---|
| Candidate-SHA | 候选的完整Git提交ID；没有覆盖实际输入的固定提交时如实说明，并以Source-Identity-Ref固定快照/差异，不以HEAD冒充实际源码 |
| Source-Identity-Ref | 实际源清单、必要差异/快照及构建输入身份的权威入口 |
| Build-Config-ID / Build-ID | 实际配置及本次构建标识，二者用途分别说明；无构建结果时不得编造 |
| Evidence-Ref | 相应总结、报告或必要原件入口；按本文第9节保留，不强制另建证据包 |
| Verified-Scope | 实际验证范围、结果、复用及未测事实，不能由字段名自动推出PASS |
| Merged-SHA | 合入完成后记录的最终提交ID及对应PR，不预写提交自身尚未生成的SHA |
| Target-Board-ID | 仅适用板测时记录实际板卡标识；未板测记NOT_RUN，序列号未知如实记录，不填示例板卡冒充现场 |

提交消息如采用Git trailers，在正文后空一行，以键值字段直接结尾，不使用以“--- ”开头的装饰分隔块或末尾横线包围字段。该格式会被标准trailer解析器当作分隔/正文边界，影响提取。PR正文可以使用表格或代码块展示，但解析约定必须明确；模板本身不代表自动强制校验。

合并时保留候选和权威追溯入口；合入后在同一权威记录关联最终SHA，利用PR/Issue链接形成可追溯关系。未部署自动脚本时如实人工记录，不声称自动完成。原始被测身份保持，后续合入映射作为新记录关联，不倒填旧报告。测试与指定成员/AI接受记录须对应真实事件、归属和范围，元数据标签不能代替测试或批准。

## 6. 接入、组合检查与可选自动门禁

收到可用候选即按原任务交指定执行人接入测试，重要模块的非作者判断结合实际接入结果，不等待与当前路径无关的材料。本页只要求权威集成基线、工程入口及准确候选可追溯，不固定由某一成员独占总工程维护、构建或现场操作；执行人沿原任务记录。隔离构建按第2节管理，不要求每次全量重新编译。OOC、增量实现等按实际适用性选择，局部结果不能替代整机共享资源和物理实现检查。

自动检查按成本和风险分层，部署后才称为自动门禁：

- 轻量检查：必要源/接口生成一致性、配置、约束和适用静态检查。
- 受影响验证：新功能及相关接口/边界用例，按现行板上返修例外选择仿真或回板。
- 重要工程增量：实际综合/实现资源、适用setup/hold、约束覆盖、CDC/RDC和DRC；复用有效同配置run，不每个PR强制完整OOC、覆盖率或长稳矩阵。

资源硬上限来自项目及模块预算，超出即处理，不等超过10%才处理；估算误差另行分析，不以统一百分比代替器件可实现性与余量。综合时序是估计，不能标成物理收敛；实现须核适用setup/hold（WNS/WHS及相关违例）、约束覆盖和例外依据，不能仅看WNS。覆盖率和耐久时长来自验收目标，不规定统一90%、100%或72小时。

模块交付前按变化风险取得必要约束、功能及可用局部资源/时序信息，明显已知问题由原任务处理；不统一强制所有PR先跑OOC且WNS≥0才准接入。Stub只用于明确限定的接口/结构检查，不能代表被替代逻辑的实际资源或时序；总工程需核全部真实逻辑，不能把黑盒缺项当余量。

报告缺失、陈旧、候选不符或解析失败时，所需检查记为未完成/失败，不把缺报告算0违例。阻断只限真实受影响路径；CI通过不能替代重要模块非作者判断和实际板测。PR Markdown模板用于提示填写，本身不是强制必填表单；平台检查/保护规则必须实际启用并核验。

## 7. 合并、基线同步与增量返修

取得准确范围认可及有效集成授权后，由获授权成员合入，默认squash。同步已共享/已审分支时保留公开提交身份，通常merge集成基线；不通过强推或重写共享历史使已审SHA失效。发生冲突时检查解决后的实际组合及受影响行为，不仅检查原分支头。

squash后main SHA可能与被测候选不同，记录候选→合入提交的源码/配置对应关系并做相称组合验证。不能仅因候选不在main祖先链就认定漏合；也不能改SHA标签就把旧板测结论转给不同内容或配置。

对应记录按[统一版本映射](#version-mapping)保存；有冲突解决、组合输入或配置变化时，以实际合入内容判断影响并补必要检查，原报告仍保留其原候选与声明范围。

merge表示变化进入基线，Issue只按真实完成标准关闭。约定板测或系统验收仍待完成时用关联说明，不以Closes自动关闭整个任务。返修留原Issue/PR，首次审完整申请范围，后续审增量；同问题最多三轮自动返修、连续两轮无进展停止等累计边界不变。

## 8. 冻结候选、正式发布与回退

需要交付时冻结准确候选及配置，冻结后围绕缺陷修复、物理实现和验收推进；若使用短期release分支，相关修复必须回到持续集成基线。正常main合并不逐次生成正式Tag。

取得适用发布授权后创建带注释的Tag（annotated Tag）和GitHub Release，绑定准确源码SHA、实际构建/配置ID、必要未提交差异及实际构建输入、器件/工具/IP/依赖、完整工程与匹配硬件/软件产物、产物哈希、报告索引、已测/未测范围和简短运行/恢复步骤。正式发布源码应落在固定提交；额外构建输入须固定归档，不能把dirty构建写成干净提交结果。板上可读版本/构建标识按工程合同实现，Git SHA和构建日期不能单独证明实际加载身份。

正式Tag不移动到新内容冒充旧版；撤回/更正说明原因并使用新版本。测试/预发布明确状态，项目正式验收按原系统目标执行。回退采用已知可用的匹配版本与配置，或按授权通过revert PR形成新提交；保留历史与故障记录，不reset或强推main。代码回退与现场重新加载分开授权。

<a id="build-identity"></a>
### 构建身份、发布清单与板上回读

构建记录采用“固定实际输入与配置 → 生成构建ID → 正式工具构建并核实际引用 → 计算产物哈希 → 发布清单绑定 → 按适用节点回读”的顺序。源码提交只是身份的一部分；源清单、外部依赖、IP/BD/XDC、初始化数据、宏、顶层、器件、工具及实际策略都须对应本次构建。输入变化生成新的构建记录，缓存/DCP复用须仍适用于这些输入，不把旧run重新贴成新候选。

板上标识机制按现有接口合同及器件能力设计，本文不预占0x00等地址或规定统一位宽。明确寄存器块总宽度、构建ID字段宽度、偏移、字序/端序、编码和读取方式；64位字段须有对应读法，四个32位寄存器合计128位。32/64位截短SHA可辅助识别，不能称完整SHA或作为唯一验真依据；构建ID需在交付范围唯一可追溯，截短标识有清单消歧方法。日期/时间戳只作辅助，并明确格式及时区，不能区分所有同日构建；语义版本位域若采用须定义分配与取值范围。

身份可由独立生成内容或正式工具支持的标识机制提供，不为每次构建手改既有RTL/厂商产物。构建前输入/配置ID与构建后产物哈希分开：最终bitstream SHA256在生成后计算，保存在外部清单，不把最终文件自身哈希嵌入同一文件造成自引用。CRC或流水号不单独保证身份唯一。

发布清单可沿已有机器可读清单扩展，不另建重复台账；对应关系至少包含：

| 信息 | 清单中应记录的内容 |
|---|---|
| source_git_sha / source_identity_ref | 完整源码提交ID及实际输入、快照/必要差异入口，不能仅记录工作区HEAD |
| build_id / build_config_id | 实际构建和配置标识；配置/工具/器件及依赖沿清单绑定，字段无法确定时如实UNKNOWN |
| source_dirty / release_status | 实际构建输入的未提交变化及候选状态；无关文档脏修改不自动判构建脏，未跟踪/ignored或外部实际输入变化不能漏记；未知不默认false |
| expected_reg_values / register_layout_ref | 已实现身份字段的预期值及读法/接口版本；尚未实现如实UNVERIFIED，不造读回值或地址 |
| artifact hashes / evidence_ref | 生成后实际bitstream及配套LTX、软件等适用产物的SHA256/入口，以及相关原始记录、已测/未测范围 |

工程调试可使用身份明确、输入受控的未提交候选，记录准确快照与差异；正式发布固定源码及必要依赖，不能把dirty输入包装成干净提交。Release状态与ILA/Debug能力分开记录：正式版本可保留必要观测并计资源/时序，不因有ILA就判非正式。

新加载、候选/配置切换或板卡交接后先核适用身份，正式验收前保存板卡、实际加载产物/软件/配置及回读比对结果；同一加载会话身份未变时复用有效核对，不要求每个小用例重新读取。脚本可按工程实现自动比对清单预期值，但部署和实际运行后才声明自动化。读取失败、未知或不符应如实记录，暂停依赖该版本身份的结论并查清，不把缺回读当匹配，不自动停掉无关路径。

回读匹配支持身份字段与清单对应，不能单独证明全部内部逻辑、实际源引用或功能正确；Git SHA不同也不能直接判错版本，先核被测候选与squash合入映射。上述要求是交付身份管理细则，寄存器、构建脚本、读回工具和真实验证须在相应工程任务实现，本次文档更新不声称已具备。

## 9. 失败留档：总结为主、必要原件为辅

默认在原Issue/PR或已有报告留下简短总结，文本、图表、截图均可；不为每次路径、脚本或小修失败新增报告包。总结应能说明：

- 输入来源及关键参数，随机用例适用时记录种子或用例ID。
- 当时的准确版本、配置、工具及发生阶段。
- 实际异常、主要现象和影响；原因未定位则如实注明。
- 采取的修复/处置、复验条件与实际结果，以及剩余未知。

已解决且记录足以复盘、余下材料无诊断或复核用途时，不要求永久保留失败完整工程、整个运行目录或全套波形。仅在问题仍未定位/仍需诊断、现场难以再次获取，或原件仍用于定量复核/验收时，保留对应的最小必要输入、日志/报告片段、波形或样本，并说明用途与入口；不因此扩大为全量现场保留。

失败、拒绝、超时和缺失的事实与统计口径必须保留，不挑成功片段、不删失败事实后改写PASS。总结/截图可记录异常；若某项数值结论需要源数据重新计算，则保留该项必要源数据。此原则不降低最终验收所需的真实证据要求，也不要求把全部历史失败原件永久保存。

不再需要的失败中间输出可以纳入[受控清理](generated-artifacts.md)：先确认总结已保存、无未结诊断/复核依赖、无独有未保存成果，并核授权、精确路径、链接及占用。只剩唯一必要原件时仍须保护。清理仅执行核实无依赖的准确对象，不倒填或改写历史记录。
