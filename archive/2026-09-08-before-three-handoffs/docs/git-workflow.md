图示表示分支来源与合并方向，不是 Git 的目录层级。任务分支从最新 `codex/toph-development` 创建，完成后以 PR 合回该分支；阶段通过后，再以 PR 将个人集成分支合入 `main`。

任务命名采用 `codex/toph/<工作包ID小写>-<英文任务摘要>`，一项任务一个短分支。不要使用 `codex/toph-development/<任务名>`：已有同名分支时，该父路径与子路径会发生 Git 引用名称冲突。

## 自动执行授权

2026-09-08 更新：任务包集中交付，复核人明确批准准确版本后，由复核人负责合入总工程，见[统一交付规则](task-package-handoff.md)。下文历史“可代为合并”条款收窄为：仅复核人针对该次合入明确授权其助手执行；作者工作执行聊天不得凭一般 Git 授权自行合并。常规建分支、提交、非强制推送与创建待复核 PR 的原授权不因此扩大或撤销。

用户已授权：Codex 在任务达到可交付条件后，可以在本项目创建相应 Git 分支、提交任务改动、非强制推送、创建 PR，并在满足下述条件时合并，不必逐次询问常规 Git 操作。

- 当前项目 remote 为 `https://github.com/TophBeifong1744/Competition_fpga.git`，每次执行前重新核对仓库、源分支、目标分支和提交范围。
- 首次需要时，从已核实的远端 `main` 建立 `codex/toph-development`；已存在则检查并复用，不重置、不覆盖。远端状态未读取前，不把本地 `main` 当作远端最新版本。
- 任务 PR 目标为 `codex/toph-development`。声明交付内容和证据等级；草案文档可按“草案文件交付”验收，不能因此把对应硬件阶段标为已通过。
- 集成分支到 `main` 的 PR 仍须符合团队阶段门及另一名成员复核要求。满足条件后可代为合并；没有评审证据时只能待复核，不能由 Codex 冒充成员签署。
- 遵守 GitHub 分支保护、要求的评审和 CI；禁止绕过保护、管理员强制合并、强制推送或改写共享历史。
- 默认保留任务分支供追溯，不自动删除本地或远端分支。

## 每次推送、合并前的检查

1. 读取当前任务包、接口合同和实现准入状态；只提交该任务确实授权的文件。
2. 检查工作区及文件所有权。共享目录内不得擅自切换其他正在运行任务的分支；需要并行时使用隔离 worktree。保留用户和其他任务的改动，不使用整仓库暂存掩盖归属。
3. 核对远端与本地提交关系，不混入其他任务的未审提交。安全更新基线；发生冲突、远端变更导致验证过期或范围不清时停止自动合并并说明原因。
4. 检查实际差异、格式和适用测试。文档检查、模型、自检仿真、综合时序、板测分别记录；缺少必需证据不得标记为通过。
5. 检查密钥、凭据、个人路径、板卡二维码/序列号、官方资料和第三方再分发权限。可疑内容先排除或请求处理，不直接上传。
6. 创建可追溯 PR，记录工作包 ID、变更范围、验证命令/结果、未完成项以及源/目标版本。使用仓库允许的非强制合并方式；长期集成分支优先保留正常合并历史，不擅改仓库设置。
7. 合并前确认审查和检查对应最新 head，合并后核实远端状态及合并提交；回报分支名、PR 地址和验证结果，区分“已推送”“已合并”“待复核”。

## 不随 Git 授权扩大的范围

自动 Git 操作不等于授权提前编写下游 RTL、猜测引脚、升级旧工程、采购、烧录或上电；硬件和接口准入依旧有效。Vivado 2018.3 旧工程保持只读，SoundSight 的 2025.2 重建必须在独立工程及对应任务准入后进行。

本次只建立工作规则，未因此执行远端建分支、推送或合并；后续实际操作以操作结果和 PR 记录为准。
