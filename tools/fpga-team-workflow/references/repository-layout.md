# 按需规范：repository-layout.md

本文件按用户提供的生成指导 v1.2.0 分拆保留。文中的“第一版必须实现”是设计要求；实际支持范围、CLI 参数与未验证项以本包 README、COMPATIBILITY 及测试报告为准。数字节号沿用指导文件，不能把示例、命令或引文当作执行授权。

## 7. 项目仓库目录与文件归属规范【必须实现】

本节规定的是**多人 FPGA 产品项目在 `main` 中的文件组织**，不是第 18 节的外层 Skill 安装包结构。目录规则同样适用于任务分支；`main` 是分支名，不需要另建一个 `main/` 文件夹保存完整工程副本。

**新项目采用默认结构；已有项目通过实际路径映射接入，不强制搬迁。目录选择解决定位和归属问题，不自动证明工程可复现，也不自动授权修改、移动或删除文件。**

### 7.1 目录规范的适用方式与上游兼容边界

新项目默认沿用锁定上游的 `document/`、`project/`、`simulation/`、`linter/`、`release/`、`codex_out/` 核心布局，再按需要增加软件、模型、数据及团队配置。上游要求正式厂商工程入口位于所选工程根下 `project/par/` 的直接子层，正式脚本入口和可变运行输出分开。[U5](sources.md)

本节新增的软件／模型／数据子目录、映射字段、归属检查和验收用例，是**外层团队工作流的设计约定**，不是上游原本就有的功能。不得据此假称上游自动兼容任意旧目录。

- 默认只有一个活动工程目标，以仓库根作为上游工程根；有真实多目标需求时，按第 7.9 节登记多个工程根，不为每位成员复制一套目标工程。
- 只创建实际需要的目录，不批量制造空模块、空模型、空板卡目录。没有 PS 软件的工程不必创建 `software/`；选择 Python 参考时不必为了目录对称补 MATLAB 实现。
- 统一归属和入口，不强制把所有代码放到同一层级。现有 `docs/`、`rtl/`、`constraints/`、`vivado/` 等名称可保留，经配置映射到对应职责。
- 目录存在不等于有有效能力；空 `.xpr`、占位 bitstream、伪造报告和“生成目录成功”均不能冒充真实工程接入。
- 任何重新布局都是单独、获授权的迁移变更。先确保旧入口和唯一数据可恢复，再更新路径、filelist、脚本与必要证据；不边修功能边顺手搬全仓。

### 7.2 新项目默认目录树

图中 `[G]` 表示受控输入或精简持久记录，应按需进入 Git；`[L]` 表示本地生成／下载内容，默认不提交；`[M]` 表示混合区域，必须逐项按来源判断；`[O]` 表示可选。`[L]` **不是可任意删除**，独有数据和失败证据仍受保护。GitHub 通常只显示实际纳入版本控制的文件，图中的本地输出目录可由工具运行时创建。

```text
<repository-root>/

├─ AGENTS.md                         [G] 简短项目约定；不复制整份工作流手册
├─ .gitignore                        [G] 经过输入遗漏检查的忽略规则

├─ team-workflow.yaml                [G] 成员、归属、布局映射、model_policy 等策略
├─ workflow-lock.yaml                [G] 外层／内层 Skill 的准确版本与来源
```

`project/sdc/` 是为了兼容上游的目录名，不要求把 `.xdc` 改成 `.sdc`。图中 `vsim.do` 来自锁定上游的规范脚手架；实际采用何种仿真器仍须核实当前入口，不因目录名或空脚本就声称 ModelSim、Questa 或 XSim 已可用。[U5](sources.md)

模型候选目录和推荐规则保存在现有 `team-workflow.yaml:model_policy`，不增加另一份重复模型表。实际账号／客户端能力可按需缓存为 `.local/model-capabilities.yaml`；含私有信息，不提交。校准结论可放 `document/verification/` 的短记录，详细用量与运行原件仍按证据政策保存。

`project/script/` 与 `simulation/script/` 应保持上游要求的入口文件集合。协作辅助代码放仓库级 `scripts/` 或 Skill 包内，不往这些正式入口目录随意加入导出库、波形、临时脚本和多个未经指定的构建入口。

### 7.3 每类目录的受控内容、本地内容与责任

以下是文件归属的默认政策。**“生成过”不等于“可丢弃”；只有依赖完整、重建路径有效，才能认定可再生成。** 模块负责人维护其输入；运行者对当次输出身份负责；归档责任人确保必需证据可访问，不用一个全局“清理人”替所有人判断唯一数据。

| 目录／对象 | 进入 Git 的受控内容 | 本地生成、默认不提交的内容 | 归属与特别要求 |
|---|---|---|---|
| 根 README／AGENTS／团队配置／版本锁 | 正式入口、规则、布局及模型策略、可共享配置和锁版本 | 凭据、本机安装备份、聊天缓存 | 协调或维护负责人；不在配置中伪造批准或实际模型设置 |
| `.github/` | 必要模板与 CI 定义 | CI 工作目录、下载缓存、全量运行附件 | 仓库维护人；不把无 EDA 的绿灯当工程通过 |
| `document/` | 合同、关键选择、图示、短验收摘要、原始证据索引 | 重复导出、完整成功日志、临时截图堆积 | 对应内容负责人；Issue／PR 状态不再抄一份 |
| `project/rtl/` | 手工维护的 RTL、package、include、正式 wrapper | 工具自动生成且可再建的 HDL 副本 | 模块负责人；每个源文件有一个权威路径 |
| `project/ip/`、`project/bd/` | 选定的权威配置／recipe、自有 IP 源、必需依赖及许可 | 已证实可再生的 output products、导出副本 | IP／集成负责人；锁定 IP 例外见第 7.4 节 |
| `project/sdc/` | 生效的 XDC／相应厂商约束、必要引用 | 工具分析结果和报告副本 | 约束负责人；原始约束不能被缓存规则忽略 |
| `project/script/` | 正式入口、配置、源码／编译顺序清单、真实重建流程 | 日志、波形、临时环境探测输出 | 构建负责人；不存未经核实的个人绝对路径 |
| `project/par/` | native-project 模式需要的 `.xpr`、源目录和已登记源输入；其他按证明选择 | 可再生运行数据库、缓存、报告、script 模式可重建入口 | 混合目录；禁止整体认定为缓存 |
| `simulation/tb/`、`simulation/script/` | TB、checker、独立验证模型、案例及真实仿真入口 | 实际激励展开结果、波形、编译库和运行日志 | 验证资产负责人；修改资产的人不自签其接受结论 |
| `simulation/work/` | 默认无；确有受控源则先纠正分类或登记例外 | 正式仿真导出和运行状态 | 执行者；失败证据先归档，清理需明确授权 |
| `linter/` | lint 脚本／filelist、经核查的边界描述 | 当次 lint 输出写入已声明诊断区域 | 工程负责人；边界描述不能冒充真实功能实现 |
| `software/` | 自有源码、实际需要的项目元数据、平台／BSP 配置、依赖锁与构建方法 | 可再生 IDE 状态、BSP 导出、编译产物、整套安装 SDK | 软件负责人；不能按“Vitis 文件”统一忽略 |
| `models/` | 一个主要黄金参考、数值约定、实验源码、种子／配置与依赖 | 派生大数组、临时图、批量输出 | 模型负责人；软件与 RTL 引用同一参考，不复制维护 |
| `data/fixtures/`、`data/manifests/` | 小型必要数据与大型数据的不可变身份、合法来源和取用方法 | 重复下载的大数据、处理缓存 | 数据负责人；大型原始数据存在本地不等于已有备份 |
| `scripts/` | 仓库级机械检查、取数或证据汇总辅助程序 | 运行日志、下载产物 | 对应维护人；不要重写另一套工程流水线 |
| `release/manifests/`、`release/golden/` | 发布清单、依赖、配套版本、验收范围；必要小型基线 | 大型基线镜像、固件、压缩包可转受控归档 | 发布负责人；基线不是当前源代码的第二份副本 |
| `release/output/`、`codex_out/` | 默认不直接提交完整目录；必需证据归档后用索引引用 | 产物包、诊断实验、缓存、上游原生证明材料 | 执行／交付负责人；Git 忽略不解除保存证据义务 |
| `.local/` | 不提交真实本机内容；可另给不含密钥的示例 | 私有路径、模型可用性／观测缓存、凭据引用、本机事务信息 | 本机成员；不得用于伪造目标、权限、模型生效或批准 |

是否需要 Git LFS、专用制品存储或额外依赖仓库由真实规模决定，不默认增加新平台。大型必需输入即使不在普通 Git 中，也必须有准确版本、校验信息、访问权限和合法来源；不能仅写“向某同学要文件”。

### 7.4 FPGA 容易误分类的文件必须单独处理

#### 7.4.1 `.xpr`、`.srcs` 与重建脚本

每个工程明确采用一种主要版本控制策略，且验证过真实重建入口，不并行维护两份可以独立修改的工程真相。

| 策略 | 默认受控输入 | `.xpr` 和运行目录的处理 |
|---|---|---|
| `script`：脚本重建工程 | 真实完整源码、配置、依赖、filelist 和重建 recipe | `.xpr` 可以由官方工具在 `project/par/` 直接生成；仅在重建证明有效后按精确路径忽略 |
| `native_project`：保留工程源 | `.xpr`、工程需要的 `.srcs` 内容、外部源码和配置 | 保留已确认的受控工程文件；只排除已识别可再生内容，不忽略整个 `par/` 或 `.srcs/` |

新项目可优先评估 `script` 方式以减少工程状态重复；**它不是“只存一份 Tcl 就不需要源码”**。已有工程保留现行策略，不能为了套模板自动删除已受控的 `.xpr`、IP 或 BD。AMD 文档分别给出脚本式与源文件式管理方法，且要求验证从受控输入重建。[V1](sources.md)、[V2](sources.md)

如果 recipe 尚未建立或没有通过重建验证，标记相应能力未验证，保护现有必要文件。不能先忽略源文件再期望日后补救，也不能假设新版本工具可以重建任何旧工程。

#### 7.4.2 IP 配置、锁定 IP 与 BD

普通 IP 保存实际 `.xci` 与相应 IP 来源／版本，或经验证可重建同一配置的 recipe；自定义 IP 还要保存真正自有源文件、打包定义及许可，不只保存一个可见名称。

没有可用旧版 IP 仓库、存在锁定 IP、加密核或不可再生成的 checkpoint 时，原本看似“生成物”的文件可能已经是必需输入。将它登记为受控依赖，进入 Git 或版本化外部制品，不因扩展名而忽略或清理。AMD 对 IP 仓库缺失时保留 output products 有明确说明。[V3](sources.md)

BD 选择本次权威 `.bd` 或重建 Tcl；保留该工具版本所需的相关依赖。不得让原生 `.bd` 与人工维护的 Tcl 各自变化却都称为唯一来源；允许保留明确派生的导出副本，但须标记来源并验证一致性。具体哪些 BD 附属文件可再生，应按锁定 Vivado 版本和实际重建结果判断，不把某版本规则套用所有版本。[V4](sources.md)

#### 7.4.3 wrapper、初始化数据与硬件／软件产物

- 工具托管 wrapper 作为派生产物处理；手工维护的 wrapper 是源码。编译清单只能选正确的一份，不同时加载同名受控副本与自动生成副本。
- `.mem`、`.coe`、ROM 镜像、标定常量等可能是功能必需输入；不能全局写 `*.mem`、`*.bin` 就当作缓存忽略。不能再生的输入须受控或有固定外部身份。
- `.bit`、`.bin`、`.mcs`、`.xsa`、`.hwh`、`.elf` 通常按**实际用途**进入发布输出或固定依赖归档。默认不反复提交每次构建的全套二进制；外部交付且无法本地重建的文件按必需输入管理。
- 软件平台生成物与人工维护的 BSP／驱动配置分开。Vitis 工作空间中有自有源码时不能忽略整目录；先识别实际版本和工程文件归属。
- 一次发布的 bit／XSA／ELF 或 bit／hwh 对应同一兼容构建，`release/manifests/` 记录映射。源文件哈希不自动证明板卡实际加载身份。

### 7.5 已有项目通过路径映射接入，不复制成“标准副本”

布局配置放入同一份 `team-workflow.yaml` 的 `layout` 节；不要再维护一份字段相同、可能冲突的 `paths.yaml`。下面是**示意旧项目**，所有路径必须由实际读取核实，不能当作用户现有目录。

```yaml
layout:
  schema_version: 1
  mode: existing
  upstream_project_root: .
  document_root: docs
  project_control: native_project
  project_entry: fpga/prj/system.xpr
  rtl_roots: [fpga/rtl, common/hdl]
  ip_roots: [fpga/ip]
  bd_roots: [fpga/prj/system.srcs/sources_1/bd]
  constraint_roots: [fpga/constraints]
  tb_roots: [verification/tb]
  model_roots: [algorithm]
  software_roots: [firmware]
  fixture_roots: [testdata/small]
  filelist_refs:
    product: fpga/scripts/sources.txt
    simulation: verification/scripts/sources.txt
  entry_refs:
    build: fpga/scripts/build.tcl
    simulation: verification/scripts/run_sim.tcl
  runtime_roots:
    formal_build: fpga/prj
    formal_simulation: verification/work
    diagnostics: codex_out
    release_output: artifacts/output
  source_exceptions:
    - fpga/prj/system.xpr
    - fpga/prj/system.srcs
  adapter_status: UNVERIFIED
  adapter_evidence_ref: null
```

字段语义：路径默认相对于仓库根，`upstream_project_root` 单独表示交给上游的工程根。`entry_refs` 是入口文件引用，不是允许任意执行的 shell 字符串；具体命令、工作目录和工具版本由核实后的适配器决定。空数组表示本项目不适用，`null` 表示未配置／未核实；两者不得随意互换。

`source_exceptions` 列出运行区域内实际受控输入，供清理和忽略规则优先保护；它不是“自动把整个目录都提交”的指令。登记了包含源文件的父目录时，默认先保护整项，不在没有更细归属证明时清理其子项。

**映射只是定位合同，不代表上游的硬编码脚本已经支持映射。** 旧工程可先只读检查；实际构建前，须验证当前桥接器能使用正确入口、路径、依赖与输出，同时不违反上游适用约束。上游要求规范化的脚手架／自动检测不能靠改配置伪装已满足。[U5](sources.md)

如果当前上游或桥接器无法可靠操作该布局，就报告不支持的动作：继续可完成的只读工作，或在单独授权下增加最小适配／迁移。不得偷偷复制完整工程，不使用未经验证的 junction／可写硬链接伪装兼容，也不把多个目标中随便找到的 `.xpr` 当作正式入口。

接入至少完成：核实实际入口和 source view → 识别输入与输出混合区 → 配置映射 → 检查忽略与保护项 → 验证相关真实入口 → 保存适配范围与证据。项目已经提供的事实不重复询问。

### 7.6 忽略规则必须经过反向检查，不能只看工作区“变干净了”

下面只是**新建、尚无唯一数据的默认布局样例片段**，不是可盲目覆盖已有 `.gitignore` 的完整模板。只有目录内已确认没有受控输入时才启用相应条目；旧项目按映射和实际工具版本生成精确规则。

```gitignore
# 本机配置；示例配置应另存受控位置
/.local/

# 上游诊断／正式仿真的本地产物；必要证据仍需另行归档
/codex_out/
/simulation/work/

# 已确认输出区，不代表授权删除
/software/build/
/software/work/
/models/output/
/data/local/
/release/output/

# 仅限已确认可再生的 Vivado 运行状态；不整体忽略 project/par
/project/par/.Xil/
/project/par/*.runs/
/project/par/*.cache/
/project/par/*.sim/
/project/par/*.gen/

# 故意不通配忽略 .xpr、.srcs、.xci、.bd、.mem、.coe 或 .dcp
# script 方式若要忽略 .xpr，验证 recipe 后再添加真实入口的精确规则
```

采用这段规则前，检查 `.gen` 等目录里是否存在锁定 IP／必需输入。若有，先保护和归档，不用规则隐藏缺失。样例未覆盖所有工具输出；需要按实际输出登记补足，而不是假装一个模板适用所有版本。

必须验证两组情况：**应提交的源文件不被误忽略；应忽略的可再生成文件不会混入交付。** 可用 Git 的 `check-ignore` 查询实际命中规则；默认它不报告已跟踪文件，检查规则本身时应理解 `--no-index` 的语义，结合 tracked／staged 清单判断。[G7](sources.md)

不要依赖被排除父目录下的简单 `!文件名` 反选来保护源文件；Git 对已排除父目录的再包含有限制。已有受控文件也不会因新增 `.gitignore` 自动退出版本历史。[G5](sources.md) 测试须包含源文件白名单和“缓存里有必需输入”的反例。

`.gitignore` 只影响版本跟踪，不授权删除；不可替代的采集数据即使被忽略也必须保护。`cleanup` 默认只处理工具拥有且已确认可再生成的诊断缓存；正式 `project/par`／`simulation/work` 清理遵守上游的明确 clean 授权与路径核验要求。[U5](sources.md)

### 7.7 目录结构必须服务于按需检出，而非制造另一套副本

模块按功能命名，不按成员姓名、临时日期或任务号长期保存整工程。默认不建 `main_copy/`、`member-a-project/`、`task-42-full-project/`、`final_v2_final/` 等并列活动源。

同一模块的产品源码、测试、模型可以分属对应职责目录，通过 filelist／配置关联。为“方便交包”把它们再复制到一个工作包目录并独立修改，属于不合格做法。研究候选保留独立算法／配置即可，公共代码仍引用同一来源。

以局部数值模块为例，稀疏范围可包含：

```text
project/rtl/<module>/        + 实际引用的公共 package/include
simulation/tb/<module>/     + 必要共享 checker／验证模型
models/<reference>/        + data/fixtures/<case>/
project/script/             + simulation/script/
document/ 中本次必要合同  + 团队配置、锁文件及实际适用 Skill 指令
```

这不是通用可直接执行的 sparse 命令。完整工程 filelist 可能引用范围外模块，工具 IP 流程也可能依赖额外目录。模块任务应选择经验证的模块入口／filelist；无此入口时先补适配或扩大检出，不裁掉真实依赖后继续声称完整构建。

`layout` 提供定位，实际 filelist／导入关系提供编译依赖。不能每次再维护一份手写全仓依赖清单；对未知依赖保持未验证。共享模型、数据和不可写缓存可按身份复用，可写运行数据库仍隔离。

### 7.8 原始数据、证据与发布的文件归属

大型数据不默认进源码历史，但须保存可由下一成员取得的持久入口、内容校验、来源／配置、版本、许可或隐私限制及保留安排。可公开的小型 fixture 可以进 Git；唯一采集原件不因在 `data/local/` 就变成缓存。

`document/evidence/` 保存短摘要和证据索引；上游原生 `task-contract`、`run-manifest`、`simulation-evidence` 等仍按其真实运行身份产生。交付前把必要原件转存至受控归档并验证访问，不把全部 `codex_out/` 反复提交，也不只给作者电脑上的路径。

`release/manifests/` 指向准确源码、工具和配套产物；`release/output/` 是本地组包区域。归档 ID／定位应稳定，不能只保存即将过期的签名下载地址。是否删除本地副本依据已有可验证归档、保留规则和授权，不因上传命令成功就自动删除。

发布清单提交与实际产品代码提交可不同，应明确记录 `source_commit` 和内容身份映射，避免为了让清单写入自身提交号而反复制造提交。添加不影响输入的索引不要求重跑全部工程，但真实入口／配置变更仍需影响检查。

### 7.9 多板卡、多顶层与多工程按需扩展

单目标项目默认使用第 7.2 节；不要因团队成员增加就复制更多完整工程。只有真正不同的器件、板卡或独立顶层才登记多个工程目标。

有此需求时，项目配置可增加 `targets`，每个目标有独立 ID、工程根、真实入口、part／工具依据和运行区域。新规范化目标可以放在 `targets/<target-id>/`，其内部保持上游所需的 `project/`、`simulation/` 等结构；这些是不同正式目标，不是 `project2` 之类随机副本。[U5](sources.md)

公共自有 RTL、模型和小数据仍只保存一份，由各目标的真实 filelist 引用；不同目标的可变 IP output products、运行数据库和仿真库不得共用。取用某目标时还要检出其跨目录公共依赖。

每次交给上游一个明确目标根，不从整仓多个厂商标记中猜测。第一版可以只实现单目标执行和多目标显式选择；未做多目标自动适配就保持未支持，不能冒称“通用”已经覆盖所有组合。

### 7.10 初始化、接入检查与路径迁移的验收

外层已有五种入口不增加新的强制审批阶段。初始化可在 `plan/work` 的明确授权范围执行；已有项目映射检查由 `doctor` 或工作区预检复用。

制作人需实现相应行为，而不是只画目录树：

1. **新项目初始化。** 已知项目事实齐全后，生成必要受控目录和配置；真实工程入口由已确认的厂商流程建立。没有器件／工具信息时可准备文档骨架，不伪造工程文件。
2. **已有项目接入。** 从真实文件识别入口与混合区，给出映射和例外；默认不移动、复制、重命名或删除产品文件。
3. **文件归属检查。** 检查 source view、filelist、被忽略源、未跟踪必要文件、重复加载 wrapper、路径越界及数据保护；仅检查“目录名存在”不算通过。
4. **干净取用验证。** 用小型 fixture 证明源文件能取全、输出不会误提交；实际工程按授权和本次层级验证重建／运行，工具不可用则明确未验证，不用结构测试替代。
5. **可选迁移。** 单独 PR 记录映射前后、受保护内容及回退；更新脚本、CI、filelist、数据引用与必要证据，核对新位置确实加载了相同受控输入。未授权时不迁移。

这些检查加入第 22 节的 `D01—D12`。布局变化、忽略规则变化及源文件／生成物归属变化，都应通过第 20 节 `maintain` 或项目配置变更完成必要验证；不能以“只是整理文件”为由绕过数据保护。
