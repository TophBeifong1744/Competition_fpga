# 按需规范：model-routing.md

本文件按用户提供的生成指导 v1.2.0 分拆保留。文中的“第一版必须实现”是设计要求；实际支持范围、CLI 参数与未验证项以本包 README、COMPATIBILITY 及测试报告为准。数字节号沿用指导文件，不能把示例、命令或引文当作执行授权。

## 16. 工作包模型与思考强度推荐【必须实现】

### 16.1 目标：同一质量门槛下，降低完整工作包总消耗

每个工作包必须有一个**自动生成的默认模型／思考强度推荐**，并标明适用阶段、简短理由和升级条件。无需每个任务都由成员重新选择，也不默认全部采用最强模型的最高强度。正式复核或决策阶段确有不同需求时，再增加阶段例外，不把一次编辑、一次命令拆成多个模型选择任务。

优化口径是：

```text
完整工作包总消耗
= 准备／实施消耗 + 必要复核消耗 + 实际返工消耗 + 切换与交接开销
```

这是评价口径，不是精确计费公式。接受质量、关键错误检出、真实证据、独立批准和安全边界不变。便宜模型造成反复错误后再由强模型全部重做，不视为有效降耗；强模型一次给出正确方案也不能因此跳过验收。

确定性工具能够独立完成的机械子步骤优先使用脚本，不为产生一条“推荐”额外启动模型。纯脚本／人工任务可以记录 `execution_kind: script_only` 或 `human_only`，模型及强度为 `null` 并说明“不适用”；这不是漏填。含工程推理的工作包不能借此绕过所需模型或内层角色。

### 16.2 本功能是外层推荐策略，不是新的工程验证等级

模型推荐策略属于外层设计，不是上游原生 `QUICK/FULL`、证据 profile 或 `claim_stage` 的替代物。模式仍按第 4 节和上游实际规则决定；**使用低成本模型不降验证标准，使用高强度模型不增加权限，也不自动证明正确。**

截至本版核对日期 2026-09-23，官方模型资料列出了 `gpt-6-luna`、`gpt-6-sol`、`gpt-6-astra`，并区分其适用定位和客户端可用性。[O4](sources.md) 本节用它们给出可维护的**初始候选方案**；不宣称这些配置已在本团队 FPGA 工作负载上取得最优性价比。

可用性必须按成员的账号、登录方式、工作空间、客户端和实际模型选择界面核对。官方资料中存在某模型，不等于当前成员已经获准使用；同一团队不要求所有账号拥有相同模型，但不能为满足便宜预算静默降低必要能力。

本指南显示“中／高／极高”时，对应候选值 `medium / high / xhigh`；实际仍以客户端支持值为准。“极高”不自动映射为 `max`、`ultra`、`pro` 或其他模式，也不默认开启 Fast／加速计费。模型名、思考强度、服务速度和登录／计费方式是不同维度；本功能只在明确授权范围调整模型及思考强度。官方配置以模型和客户端公开支持的 effort 为准。[O5](sources.md)

自然语言“请多想一会儿”或 `SKILL.md` 中写一个模型名，不等于实际参数已经切换。不得用模型自报身份代替运行配置证据。

### 16.3 先识别实际工作，再匹配配置

使用工作包已有事实判断，不额外要求人工填写复杂评分表。至少看：

| 判断维度 | 推荐时的问题 | 避免的误判 |
|---|---|---|
| 当前活动 | 固定执行、普通实现、诊断、设计参考、独立复核还是架构决策？ | 名称都是“仿真”就统一选最轻配置 |
| 需求和判据 | 合同、黄金参考、关键假设是否明确且可信？ | 把错误或未知参考当作可靠自检标准 |
| 影响范围 | 局部、跨文件、共享接口、时钟复位或跨软硬件？ | 用修改行数代替工程影响 |
| 错误代价 | 能否发现并回退；是否涉及数据丢失或实物安全？ | 一行约束修改被当作低风险文档工作 |
| 诊断成熟度 | 首错和最小复现是否已有，根因是否已证明？ | 不知道根因却让执行档反复改代码 |
| 真实条件 | 当前模型、工具、数据、权限和板卡是否可用？ | 用更强推理掩盖缺硬件、缺资料或无授权 |

推荐绑定工作包、当前阶段、执行／复核成员及策略版本；同一任务的团队默认建议与成员端实际可用配置可以不同。协调者不能把自己账号的能力当作所有人的能力；无法核对另一成员环境时保留未知，不要求传递其凭据。

同一输入、相同策略版本和相同已知能力应得到可解释的一致推荐。多数任务按规则／表格匹配；信息不足时给候选及“待确认”原因，不凭印象给精确成本或虚构可用模型。真正必要的澄清只针对未解决事实，不重问任务中已明确的信息。

### 16.4 首版候选表：少量档位，按实际案例校准

下面的档位是**外层 `routing_profile`**，不是 Codex 内置配置 profile，也不是上游的验收 profile。表中的模型组合按用户采纳的设计保留为试运行起点，推荐质量标记 `UNBENCHMARKED`，在团队校准后才可标记本地验证范围。官方建议用同一输入比较配置，并保留达到质量要求的较轻设置；本表不是官方针对 FPGA 的保证。[O3](sources.md)

| routing_profile | 典型活动 | 初始模型／思考强度 | 重要限制 |
|---|---|---|---|
| `execution` | 已有可信入口的运行协调、清单核对和结构化结果提取 | 脚本优先；需要模型时 **GPT-6 Luna / high** | 不能承担未知根因诊断、重新定义判据或复杂功能签署；降低至更轻 effort 需案例校准 |
| `routine` | 合同明确的局部实现、普通构建脚本修改、已证明根因的局部修复 | **GPT-6 Sol / medium** | 日常默认起点，不默认适用于未知 CDC、公共接口重构或高风险动作 |
| `analysis` | 有界多文件诊断、测试设计、普通技术复核 | **GPT-6 Sol / high** | 先有可信合同；发现参考／前提冲突或跨层影响时重新分流 |
| `decision` | 新关键假设、架构取舍、跨模块接口、重大重构规划 | **GPT-6 Astra / high** | 已有充分依据且影响受控时，可明确推荐 medium；高影响新决策不要先让最轻配置试错 |
| `deep` | 难解跨层故障、复杂反例、多约束架构权衡 | **GPT-6 Astra / xhigh** | 需说明深度推理要解决的具体不确定性，不作为整个项目的默认配置 |

不同模型的同名 effort 不是统一的能力或费用刻度；不能按“高大于中”推断 Luna high 一定比 Astra medium 贵或强。官方能力定位只用于筛选候选，最终以任务质量和真实可用设置为准。[O4](sources.md)

对于“仿真”，至少区分：

```text
执行已验证测试入口 → execution
定位有明确首错的局部失败 → analysis 或已证明根因后的 routine
从零设计 scoreboard／独立参考 → analysis；前提不明或高影响时 decision
判断作者和参考是否共享错误假设 → 独立回到原依据，按 decision／deep 的必要性处理
```

这里没有按固定词语强制升级。一个可手算反例已能证明错误时，直接报告事实，不再为满足“高档审查”调用最强模型重复证明。

### 16.5 一包一个默认推荐，只在连续阶段变化时调整

开工或创建工作包时生成默认推荐；同一工作包继续时复用已有推荐。只有范围、证据质量、风险、成员能力、策略版本或当前工作阶段实质变化时重新判断。纯 `status` 请求读取已有摘要，缺失时可以只读补推荐，但不自动更改远端 Issue 或客户端设置。

允许一个工作包采用“架构判断较强、实施适中、机械执行较轻、复核按风险”的阶段配置。阶段例外写在同一 Issue／PR 的推荐摘要中；不要求在每个命令前切换模型，也不为保持表格整齐强制把内层每个角色换一次配置。

若当前会话设置偏高，但剩余仅一个短机械步骤，默认让已授权脚本直接完成，不为了省一条回复重新建立整个会话。高成本常驻配置影响后续持续工作时，再在稳定检查点提示切换。

当前会话已经使用的计算不能被后续推荐追回。第一版不能承诺“尚未生成推荐前，本次请求就已自动用最便宜模型执行”。跨会话交接只传任务、版本、关键假设、证据索引和下一步，不传全部历史，也不删除独立复核所需原始依据。

### 16.6 推荐、授权与应用必须分开

第一版默认 `mode: recommend_only`：**推荐自动产生，设置不自动修改。** 同学必须实现可用的推荐输出、能力检查和手动采用说明；自动切换属于按客户端实测支持的可选能力，不能只写一句“自动换模型”就宣称完成。

```text
读取已有任务与策略
    → 核对成员端模型／effort 能力
    → 给出默认推荐、理由与升级条件
    → 用户手动采用，或在明确策略授权下使用已验证的设置接口
    → 核对实际生效状态
    → 原任务继续，验收和授权边界不变
```

建议只提供两种策略模式：

| mode | 行为 | 不允许的行为 |
|---|---|---|
| `recommend_only` | 输出建议；保留当前设置；必要时说明如何人工选择 | 因推荐结果擅改当前会话、全局 config、Agent 文件或账号计费 |
| `apply_authorized` | 仅在用户已明确授权的作用域、模型集合及单次／持续策略内，使用实测支持的接口应用 | 把配置中的布尔值当授权；跨成员电脑自动应用；越过组织限制 |

`apply_authorized` 必须能核对目标、当前配置及调用结果，保留失败／冲突处理。接口不支持、权限不足或无法核对时降为推荐，不执行猜测命令；不要借道新增 API key、购买额度或改变登录方式来实现切换。

用户对具体工作包的明确选择优先于默认推荐，但不能突破平台权限或降低工程验收要求。用户已经授权一个适用的切换策略时，不在每个步骤重复询问同一授权；实际使用仍须留有记录。用户暂不采用推荐也不单独构成工程失败；若已知当前配置不满足关键工作的能力要求，应明确风险和待处理范围，而不是继续猜测或自签。

当前官方文档说明交互式 Codex CLI 可通过 `/model` 选择模型／强度，也支持启动时指定模型；这不构成所有桌面、IDE、云端环境都支持同一种自动切换接口的保证。[O4](sources.md) 制作人只为自己实际验证的客户端实现适配。

### 16.7 推荐与实际生效分开，主会话与子 Agent 分开

至少区分以下事实，不从上一个字段推断下一个字段：

| 事实 | 含义 |
|---|---|
| `recommended` | 外层希望本阶段使用的模型与 effort |
| `requested` | 用户或受授权适配器实际请求的设置 |
| `observed` | 客户端／运行元数据能够证实的实际设置 |
| `observation_status` | `VERIFIED / USER_REPORTED / UNKNOWN / MISMATCH`，用于区分证据等级 |

`VERIFIED` 要有可信运行元数据或客户端可核对信息；用户手工回报可以记为 `USER_REPORTED`，但不伪称工具已确认。修改 config 文件只能证明配置意图，不独立证明正在运行的会话已经重载。模型回答“我是某某”不计作生效证据。

官方子 Agent 配置有继承与覆盖关系：自定义角色文件中的 `model`／`model_reasoning_effort` 可优先于其他默认设置；未显式配置时还受创建请求、Agent 默认和父会话影响。[O2](sources.md) 因此，不可仅因主会话推荐 Sol 就报告所有工程角色都在使用 Sol。

每个实际启动的子 Agent 按可观察范围记录模型／强度及设置来源；没有启动的角色不制造运行记录。第一版不需要为上游全部角色逐个定制模型，先检查实际配置和必要例外，不再增加一套同名技术角色。

若上游角色锁定配置与外层建议不同：说明差异，保留上游受控文件；走维护流程核查并批准最小适配。不得在普通工作包中临时改写已安装上游 TOML、删除角色或伪装继承生效。支持按次覆盖的客户端也要验证真实优先级，不能仅凭提示词保证成功。

缺少生效观测时仍可提供建议，并明确“实际设置未知”。低风险、已授权的普通工作不因可选用量观测缺失而被无限阻塞；对于需要能力保证或预算上限的自动模型应用，不能把未知状态算成已满足条件。

### 16.8 升级、降级与停止：靠事实，不靠固定阶梯

| 观察到的情况 | 默认处理 |
|---|---|
| 已有可信脚本正常运行 | 不升级推理，不让模型陪跑；仅必要结果摘要 |
| 简单执行变为不明首错／需要改 checker | 重新识别工作性质，推荐 analysis 或必要决策档 |
| 新公共接口、关键数值前提、跨时钟／跨软硬件原因链 | 按影响直接选足够能力，必要时跳到 decision／deep |
| 当前配置给出循环解释、没有可检验新诊断 | 先固定最小复现和原依据，再决定是否升级；无进展时停止盲改 |
| 合同、手算、参考与实现矛盾 | 独立核对前提；撤销受污染证据；不以更强模型“投票”解决 |
| 缺数据、缺工具、缺权限、板卡未连接 | 补真实条件或停止对应动作，不靠升级模型猜补 |
| 强配置已解决决策，剩余实现合同清楚 | 稳定检查点可推荐较轻配置；不要逐条命令往返切换 |
| 推荐模型不可用或 effort 不支持 | 在满足质量及授权的已验证候选中提供替代；无合格候选就报告缺项 |
| 达到约定额度／运行边界 | 按实际可观测限制安全暂停，保存检查点；不静默调用更贵模型或降低验收 |

不要求 `Luna → Sol → Astra` 逐级试遍；已知是复杂决策可以直接推荐足够配置。也不要求每次先提高 effort 再换模型，两者需要结合已有问题和总成本判断。`high → xhigh` 不是无条件质量提升保证。

模型或 effort 变化**不重置第 12.4 节的自动返修计数**；同一错误不能通过换模型、重开会话或改任务名继续无限循环。升级建议必须说明具体触发事实和期望获得的新诊断，而非“没成功所以再贵一点”。

### 16.9 与复核独立性、证据复用和版本管理衔接

负责人和复核人分别得到适合当前活动的推荐，不强制使用同一配置，也不强制使用不同模型。关键假设核查可能比作者的固定执行需要更强配置，但不是每个普通复核都默认 Astra xhigh。

**模型不同不自动构成独立性，模型相同也不自动否定独立性。** 按第 9—10 节核查原始前提、参考来源、实际实现和必要反例，非作者承担批准责任。更贵模型或更多模型的一致结论不能替代事实和试验。

仅改变参与分析的模型、effort 或推荐策略，而源码、合同、checker、输入、工具及适用依赖未变，不自动使既有 EDA 运行证据失效。若新分析发现假设错误、修改了参考／实现，或实际生成的工具命令改变，则按影响重新判定；不能以“只是换模型”复用被污染的旧 PASS。

推荐摘要和策略版本可进入交付记录；不强制每次切换产生一个 Git 提交，不修改旧运行记录中的实际设置，不让政策升级覆盖历史事实。校准模型选择的实验与正式产品验收分开记录。

### 16.10 最小记录与配置归属

一项工作包只追加一个短推荐块；普通继续不重复输出完整表格：

```text
模型建议：GPT-6 Sol / medium（routine；实施与自测阶段）
理由：合同明确、影响局部、已有可信测试入口
升级条件：发现跨时钟影响、参考矛盾或无新增诊断的持续失败
策略／校准：项目 model_policy <版本>；初始候选／已校准范围
实际：主会话 <实测或未知>；已启动子 Agent <例外或未知>
应用状态：仅建议／用户手动采用／受授权应用；不据此修改验收等级
```

团队规则与候选目录只保存在 `team-workflow.yaml:model_policy` 中，不另建相同字段的全局模型表和手工额度台账。包里只保留可复用示例；成员可用性和实际观测可缓存到 `.local/model-capabilities.yaml`，该文件不提交真实账号／凭据信息。缓存必须有检查时间和来源；成员登录、客户端或角色配置变化后重新核实。

语义判断由必要的当前会话处理；模型 ID、effort 集合、策略版本、配置冲突和缺字段等机械检查交脚本。配置、标准返回和版本引用的具体示例见第 19 节。私有缓存不是授权或平台访问权的来源。

### 16.11 以代表性案例校准，不做每包多模型竞赛

首次采用、策略发生实质变化或出现真实漏检时，在独立维护任务中选择少量代表性案例比较候选。至少包含：固定可信脚本执行、局部实现、有界首错、错误假设／坏 checker、跨模块取舍。复杂候选需要匹配其声明适用范围的案例，不以一个简单模块成功证明适合所有 FPGA 工作。

比较条件尽量一致：任务、输入、合同、工具、必要上下文、完成定义和独立评价标准相同。保留未参与调参的案例；不能把一个模型自己的答案当作唯一标准，也不能只比较成功案例或排除失败重试成本。

优先观察：接受质量、关键错误／错误假设检出、返工次数、完成总用量和耗时；人类复核成本也纳入判断。耗时区分模型等待、EDA 运行和现场等待。脚本／fixture 测试只证明路由规则，实际多模型案例才为推荐质量提供证据；两者不能互相冒充。

能从合法运行记录获取 token／credit 时再记录，未知用 `null`，不能填 0、推测隐藏推理内容或要求成员逐条手记。API 金额、Codex credit 和订阅内额度不是同一种口径，不能互相直接换算，也不因模型单价下降就报告固定节省百分比。[O6](sources.md)

只有达到同一质量门槛的候选才比较成本；存在关键漏检时不能因便宜而晋级。`UNBENCHMARKED` 是推荐待校准，不等于模型不可用，也不阻止在明确边界和正常复核下试运行；正式宣称“已验证适用于某类任务”必须有对应案例。

### 16.12 推荐策略也通过既有更新接口维护

模型目录、支持值、默认映射、升级条件、成员端兼容或策略校准发生变化时，先判断是项目配置、外层规则还是工具适配问题。使用第 20 节 `maintain`，不要为模型选择再建一套更新系统。

版本分开：生成指导文档版本、外层 Skill 发布版本、上游 Skill 版本、`model_policy` 版本是四类身份，不能一起随手改成同一个数字。添加模型候选并不意味着自动安装、购买或全员切换。成员加入时只核对自己真实可用能力；同一策略可以为不同成员给出经过批准的兼容建议。

更新要验证：旧任务仍可读、不可用模型不伪装可用、旧批准不被追改、默认不自动应用、上游角色不被覆盖、既有质量门槛不下降。禁止每个任务联网自动追最新价格和模型清单；使用已批准的本地策略，过期、缺项或用户要求刷新时再进入更新流程。

### 16.13 第一版实现边界

第一版**必须实现**推荐生成、阶段差异、具体模型／effort 绑定检查、缺项与实际设置未知的表达、升级／停止判断、交接集成、策略维护和对应反例测试。推荐功能不是单纯增加一个“由人填写模型”的空栏。

第一版**不强制实现**全客户端自动切换、精确订阅额度读取、跨成员遥测、模型竞价、多模型投票或独立路由 Agent。没有自动设置能力时提供可用的手动采用路径；不得把“仅建议”包装为“自动配置已生效”。

已有配置缺少 `model_policy` 时，保持原执行设置并提示新增功能尚未配置；可显示内置候选建议，不能偷偷写入配置。出现未知 schema 或冲突时，停下受影响的自动应用／维护动作，保留正常只读诊断及已有安全流程。
