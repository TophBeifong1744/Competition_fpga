# 按需规范：maintenance.md

本文件按用户提供的生成指导 v1.2.0 分拆保留。文中的“第一版必须实现”是设计要求；实际支持范围、CLI 参数与未验证项以本包 README、COMPATIBILITY 及测试报告为准。数字节号沿用指导文件，不能把示例、命令或引文当作执行授权。

## 20. Skill 改进与更新接口【必须可用，不只是 TODO】

### 20.1 用户应能自然地提出更新

示例：

```text
这个 Skill 每次复核都重新跑全部仿真，我希望先检查已有证据。
请为这个问题建立改进提案，暂时不要修改已安装版本。
```

或者：

```text
按已经批准的更新提案修复外层 Skill，生成候选版本并验证。
不要升级上游工程 Skill，也不要安装到其他成员电脑。
```

`maintain` 必须识别这是流程维护，不继续把请求当成产品 RTL 工作。普通“这里有点不方便”默认是反馈／提案；“按此提案修改候选源码”可以授权对应源码编辑，不需要重复询问相同范围。

### 20.2 先区分修改对象

| 对象 | 更新方式 |
|---|---|
| 外层协作规则 | 修改外层 Skill 源仓库，独立复核与发布 |
| 项目配置／默认参数／路径映射 | 更新配置、归属和必要入口验证；不必每次改全局 Skill，也不默认迁移文件 |
| 模型目录／推荐策略／校准结果 | 优先更新 `model_policy` 及必要验证；记录策略版本，不自动改变各成员运行设置 |
| 模型设置适配／子 Agent 配置冲突 | 核对官方接口、角色覆盖和实际生效；只修改获授权且受控的最小范围，不在产品任务里乱改上游 |
| 工具桥接／日志适配脚本 | 修改适配器并验证真实调用和证据映射 |
| 上游 `run-fpga-workflow` | 在维护任务中评估指定版本／提交，核对角色、schema 和行为；不私自修改已安装上游文件 |
| 确需修上游但上游尚无可用版本 | 经明确批准维护可追溯 fork／补丁，记录来源、差异、版本与许可证；不能仍伪称未修改官方包 |
| 单次产品任务问题 | 修本任务；未确认是可复用流程缺陷前，不自动上升成全局规则 |

### 20.3 外层维护协议的七个动作

这些是**待实现的外层动作**，不是官方自带的更新 API。

| 动作 | 输入 | 必须输出 | 默认边界 |
|---|---|---|---|
| `propose` | 用户反馈、示例、目标 | 去重后的更新提案和影响层 | 不改生效规则；远端建 Issue 须有相应授权 |
| `plan` | 提案、当前锁版本 | 最小修改点、兼容性、回归与回退计划 | 只读诊断，可真实查询指定上游资料 |
| `apply` | 明确编辑授权、已识别基线 | 候选源码 diff、变更说明、测试结果 | 修改候选源，不直接覆盖运行安装 |
| `verify` | 候选包／提交 | 结构、安全、反例、升级回退和代表任务结果 | 未运行部分明确标记 |
| `publish` | 通过的候选、非作者批准、发布授权 | 发布版本／tag／包及依赖锁 | 无权限则提供发布材料，不虚构远端成功 |
| `install` | 目标包、作用域、安装授权 | dry-run、受控备份、实际安装和核对记录 | 只作用于授权设备／路径，不推送到全员机器 |
| `rollback` | 已知良好版本、事务记录、回退授权 | 恢复的受控文件与核对结果 | 不回退产品源码和用户数据，不覆盖未知后续改动 |

这七种动作是接口语义，不是七个必须分别调用的 Skill，也不是七轮人工确认。一条明确授权的维护请求可以连续完成其覆盖的阶段；独立发布批准和新增权限边界仍保留。反馈及候选验证不要求先完成全套发布手续。

第一版最低要求：能生成有效提案、构造候选改动、运行验证、提供安装预览、受控安装与本机回退。模型目录刷新或默认推荐变更也走同一协议；候选策略未应用到会话时必须保持“仅建议”。远端发布可由现有 GitHub 工具或人完成，但入口、产物和状态必须衔接，不能留下一个无行为的“以后更新”标题。

### 20.4 变更请求 schema 示例

```yaml
schema_version: 1
change_id: CHG-EXAMPLE
kind: outer_rule
base_release: null
base_source_commit: null
problem: 复核对同一稳定证据重复执行完整仿真
reproducer_ref: null
requested_behavior: 先核对假设和证据身份，再选择最小有价值的补测
protected_invariants:
  - 保留非作者成员批准（项目启用时可由其指定AI代理）
  - 不弱化上游功能验收和技术终审
  - 不复用已被错误假设污染的接受结论
scope:
  include: [references/review-and-evidence.md]
  exclude: [upstream_skill, product_rtl, installed_copy]
acceptance:
  - 同一有效证据不触发无理由全量重跑
  - 错误饱和假设即使自检通过仍被阻断
  - 缺失必要证据不能被自动批准
compatibility:
  project_schema_change: false
  bridge_schema_change: false
rollback_target: null
```

模型维护可采用 `kind: model_policy`，修改 `team-workflow.yaml` 中的策略子树；客户端设置适配可采用 `kind: model_runtime_adapter`。这两个值是外层新 schema 设计，需在解析器中明确支持，不是上游原生维护类型。更新提案注明哪些模型／effort 和阶段受影响，哪些真实设置、上游角色及计费方式不得改变。

这是一条更新任务中的字段，不要求每条反馈创建多个文件。可先本地生成提案，再按授权发布为 Skill 源仓库的 Issue。外层应填入真实基线；无法确定版本时可以记录反馈，但不能盲目 apply／install。

### 20.5 更新闭环

反馈去重 → 定位是配置还是规则／上游缺陷 → 核对当前版本与约束 → 最小候选修改 → 自动与人工行为验证 → 非作者复核及成员或其指定AI批准 → 发布指定版本 → 成员在安全检查点按需安装 → 新会话核对 → 保留可回退版本。

团队只同步指定版本，不让每位成员在任务执行中自动追最新 `main`。外层升级、上游升级和模型策略更新可以分别进行，不强制一次更新整套工具链。更新推荐表不自动开启新的付费／速度模式，不让普通任务为追最新清单持续联网查询。

正在进行的工作包记录实际使用版本。正常情况下完成当前原子步骤／稳定检查点后再切换版本；发现严重规则缺陷时可暂停受影响任务，不能为追求版本一致而继续危险动作。

### 20.6 安装事务与回退必须满足

1. **比较当前状态。** 核对安装作用域、现有版本、已安装文件内容、用户修改和配置冲突；重复安装相同包应可幂等处理。
2. **先预览。** 列出新建、替换、移除的自有文件，依赖变化和需重启／新会话的提示。只读预览不改变文件、锁版本或远端状态。
3. **计划防过期。** apply／install 之前重新核对预览对应的基线指纹；期间被他人修改则报告冲突，不能继续覆盖。
4. **保留备份。** 保存版本、哈希、安装清单、事务记录和待恢复内容；不备份整套 FPGA 构建产物。
5. **安全切换。** 使用经目标平台验证的 staging／替换策略；若不能保证原子替换，必须能在中途失败后恢复到一致状态并提供恢复指令。
6. **仅修改拥有的文件。** 不覆盖无关 Skill、`AGENTS.md`、角色配置、凭据、全局 PATH 或已有用户自定义设置。
7. **核对实际生效。** 验证文件与包版本，开启新会话或按客户端要求刷新后验证行为；不能仅更新锁文件宣称运行已切换。
8. **回退保护后续修改。** 当前文件若不等于本次安装结果，视为后续用户改动，停止自动覆盖并报告；不能用全目录恢复丢掉这些变化。
9. **配置迁移可逆。** schema 变化提供迁移说明及备份；破坏兼容性的迁移不能自动执行。
10. **产品与证据分离。** Skill 回退不等于产品代码、板卡固件或工程数据回退；每种回退有独立范围和授权。

上游自己的安装／核对／备份能力应优先按指定版本复用，不能假定只更新主文件就完整升级全部角色。[U3](sources.md)、[U4](sources.md)

### 20.7 更新必须保留的防退化测试

新的规则不能取消独立批准、把缺证据变成 PASS、默认无限返修、无条件复制完整工程、强制搬迁已有项目、把混合目录中的必需输入当缓存、缩小 sparse 时删除保护数据、绕过硬件授权、伪造平台权限或改写用户历史。还必须阻止无授权改模型、将模型建议伪报为生效、通过低价模型取消必要验证、用换模型重置返修计数，以及静默改写上游角色或计费设置。

执行逻辑修复保留能暴露原错误的最小案例；纯规则/文稿调整核对代表性任务决策与冲突即可，不为文字变化制造工程测试矩阵。未经根因确认的偶发现象不自动固化为全局规则。记录可见需求、事实、修改和验证结果，不记录或要求隐藏思维链、系统指令和私密聊天。

### 20.8 版本与发布说明

外层建议采用语义化版本习惯：兼容修复、兼容新增、破坏性行为／schema 变化分开表达。版本规则是本项目约定，不等于上游的版本政策。

每次发布说明：修了什么、影响哪类任务、上游依赖是否变、模型推荐策略及适用校准范围是否变、已运行测试、未验证平台、迁移及回退方式。不能声称支持从未运行过的操作系统、客户端、仿真器或板卡。
