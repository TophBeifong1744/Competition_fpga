# 按需规范：review-and-evidence.md

本文件按用户提供的生成指导 v1.2.0 分拆保留。文中的“第一版必须实现”是设计要求；实际支持范围、CLI 参数与未验证项以本包 README、COMPATIBILITY 及测试报告为准。数字节号沿用指导文件，不能把示例、命令或引文当作执行授权。

## 9. 独立复核：先看假设，再看证据，最后决定是否重跑【必须实现】

### 9.1 复核不等于复制作者的自检过程

负责人已经跑过的测试，另一成员原样完整重跑，可能只证明“同一条件下能重复得到同一结果”，不必然增加需求正确性或覆盖率证据。

同时，独立复现可以发现漏依赖、错误源码入口、隐式环境、无法获取的输入和伪通过，因此也不能一律取消。**每次复核运行必须回答：这次要消除哪一个尚未解决的不确定性？**

默认先审合同、关键假设、变更和既有证据，再选择最小有价值的独立核查。首次完整审本次范围，不是完整重做作者开发，也不是审整个仓库。

### 9.2 三类错误必须分开

| 类型 | 示例 | 主要核查方法 |
|---|---|---|
| 实现错误 | RTL 与正确的饱和加法规则不一致 | 可信参考、边界测试、实现分析 |
| 验收资产错误 | 测试没喂入数据、checker 未执行、对拍错位 | 活动计数、首错、负例、独立小例子 |
| 前提／需求解释错误 | 作者和参考模型都错误采用回绕，真实需求要求饱和 | 回到原始需求／接口来源，独立推导和针对性反例 |

不能把第三类问题仅归为“再跑一次仿真”。如果预期本身错了，重复运行同一预期仍可通过。

### 9.3 关键假设核查顺序

1. 读取本次原始需求、接口合同、相关手册或物理条件，区分已确认事实、暂定工程选择和未知项。
2. 提取直接决定验收的关键假设，先写出少量独立预期；再对照作者结论，避免只沿用作者解释。
3. 核对参考模型／黄金向量的来源、适用条件、版本和独立性；不同语言实现不自动意味着独立。
4. 核对测试是否有能力发现“违反需求但能通过现有测试”的实现。
5. 只对发现的缺口、风险和必要复现设计追加动作。

关键假设可以包括单位、数制、溢出、舍入、通道顺序、握手接受时刻、可见延迟、复位行为、缓存所有权、时钟关系和真实场景条件。只审本次影响范围，不罗列全专业清单强迫全做。

### 9.4 示例：作者与模型共享错误假设

假设合同要求 8 位有符号饱和加法。对于 `120 + 20`，独立依据给出的结果应为 `127`；若实现和参考都做 8 位回绕，两者会一致输出 `-116`。

正确复核动作：核对原合同，手算这一边界，确认参考是否错误；必要时补一个最小反例。错误复核动作：照抄作者脚本重跑一百次，以“全部一致”批准。

负向 canary／错误注入可以证明检查器能抓住某类错误，但**不能单独证明验收标准正确**。换一个 Agent、另一位成员或另一种语言，也不能抵消共享错误前提。

模型推荐同样遵守这一点：不同模型一致不替代独立依据，Astra 极高也可能接受错误前提。关键假设复核按其判断难度推荐足够配置，但已能用一个正确反例阻断时不再启动昂贵模型重复证明。

### 9.5 哪些前提值得实施前确认

新接口、新数值约定、重要物理假设、跨模块时序、错误处理或一旦误解就造成大面积返工的前提，应在 H1／接口约定或开工阶段做一次简短独立核对。

已确认且未变化的假设直接引用，不把每个小实验变成审批。低风险细节可在交付复核时检查，不增加固定的“所有任务预审大会”。

发现原合同有误或自相矛盾时，暂停受影响的接受结论，提出合同修订与影响清单，由授权责任人决定。不能因为“不能增加验收门槛”就忽略本次正确性所必需的事实；也不能趁此加入无关新功能。

## 10. 证据复用与复核执行决策【必须实现】

### 10.1 复用的不是一句 PASS，而是有适用前提的证据

复用前检查与当前结论有关的身份：

- 需求／接口／关键假设及批准版本。
- 相关源码、约束、参数、宏、IP 配置、依赖和实际加载入口。
- 测试平台、checker、参考模型、输入数据、种子和运行配置。
- 工具、库、目标器件和与结论相关的环境条件。
- 实际运行结果、执行覆盖、原始报告可访问性和适用限制。

不要求把全部历史都重新 hash，也不因为无关 README 修改就重跑全部工程。依赖范围不明时先界定影响，不能自行认定“应该没影响”。

关键假设或 checker 被证明错误时，旧 PASS 即使文件哈希未变也不再是有效接受证据。必须标记失效原因、影响的结论和待补证据。

### 10.2 决策表

| 情况 | 默认处理 | 是否必须重跑作者全部仿真 |
|---|---|---|
| 身份、合同和相关依赖一致；证据完整；无新疑点 | 复用结果，独立核对判据与关键实现 | 否 |
| 需证明在接收人环境可复现 | 选择一个能覆盖入口和关键依赖的代表性检查 | 否，除非完整复现就是本次判据 |
| 首次交付关键功能、新接口或新增／修改 checker | 核对前提，独立小例子及必要负例，按风险补测 | 不默认全跑 |
| 原始结果不可访问、运行身份不清、测试未有效执行 | 不能仅引用摘要；补原证据或重跑相关检查 | 仅必要范围 |
| 公共接口、数值、时钟、复位、IP／约束改变 | 根据影响扩大验证，失效证据重建 | 可能，需要明确理由 |
| 作者测试与手算／手册／实测矛盾 | 撤销受影响接受结论，定位前提／参考／实现 | 先修根因，不盲跑 |
| 合并冲突生成新代码 | 重验冲突和相关行为，必要时完整回归 | 由影响决定 |
| 阶段长稳／系统判据明确要求完整运行 | 对指定集成版本按要求运行 | 是，本次有独立目的 |
| 已发现足以阻断交付的确定错误 | 集中给出事实和反例，停掉无关昂贵复跑 | 否 |

### 10.3 复核记录应短，但结论明确

在 PR 或交付入口记录：

```text
复核范围和准确版本：
关键假设／判据独立核对：依据、结论、必要反例
复用证据：ID／位置、适用理由，明确“复用，未重跑”
新增核查：做了什么、解决什么不确定性、实际结果
阻断与未验证：
批准人、批准范围和对应提交：
```

每一个高成本补跑给一句明确理由即可，不要求再写一份长篇“复核方案”。对纯文档任务，独立语义／链接检查可能已足够，无须为了“独立执行”制造仿真。

### 10.4 保留两层独立性，不完整叠跑两轮工程

内层必要的技术终审照常保留；外层指定成员对实际交付负责。外层不额外创建与内层相同的一组技术角色。

复核成员调用自己安装的工程 Skill 时，以 `ANALYZE` 和明确的复核范围进入；需要真实复现时单独描述隔离验证的授权，不能把只读请求悄悄升级为修改产品代码。要求生成正式签署性技术结论时，保留上游适用的独立 reviewer。

上游要求功能验收从独立需求与依据出发、关键检查器有负例、作者不能自签修改过的验收资产。[U1](sources.md) 外层复用这些规则和证据，不弱化它们；也不把一次上游成功结果自动转换为成员批准。

## 11. 运行身份、证据存储和更新失效

### 11.1 最少事实，尽量来自内层原生材料

优先读取上游的 `task-contract`、`snapshot-manifest`、`impact-manifest`、`run-manifest`、`simulation-evidence`、`findings-ledger` 等已有文件。[U1](sources.md)

外层只做索引／引用及必要字段映射，不另外复制全部内容。适配器不支持某个上游字段时标为不支持，不编造值。证据解析必须能报告 schema 版本不兼容。

基本身份应覆盖：源提交、必要 dirty diff／新增文件身份、需求与参考身份、相关输入、命令和工具、目标／参数、运行结果、原始证据入口。

模型建议与实际设置采用外层简短记录或可用运行元数据引用；上游 schema 没有相应字段时不私自塞入或伪造。模型／effort 变化本身不使相同输入的 EDA 证据失效；假设、checker、命令或实际输入变化则按第 10 节判断。

### 11.2 不每次 commit，仍须识别当时输入

开发中允许未提交状态运行。快照记录实际相关工作文件及新文件的内容身份，不能只记录 `HEAD` 而忽略工作树差异。Git diff 本身不包含所有未跟踪文件，快照工具必须补足实际输入清单。

正式交审默认使用已提交的干净相关输入。若测试后提交只是把同一内容纳入 Git，可建立输入身份映射而不重跑；若测试后改了输入，必须重新判断证据有效性。

运行期间输入应稳定；开始／结束检测到变化时，标记运行身份不确定，不能用首部 hash 冒充稳定快照。

### 11.3 存储与保留

团队可选 Release、受控共享存储或合适的 artifact 系统，但接收人必须可访问。大型数据保留摘要、哈希、元数据和入口，不默认进入源码历史。

临时 CI artifacts 有保留期限时，阶段正式证据应转为满足项目保留要求的归档。不能提交一个未来必然失效且无保留安排的链接作为唯一阶段证据。

源文件未变化但相对路径、入口或库映射变化时，必须核对实际加载路径。文件相同不保证执行方式相同。清理只能删除已经确认冗余的副本，不删除唯一失败证据。
