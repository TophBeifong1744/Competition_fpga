# 三人统一的任务包交付与复核规则

生效：2026-09-08，依据用户最新要求。适用于拓芙、BryanZheng802、hsc119 的全部工作包与对应聊天任务；本规则优先于旧的自动合并安排。

## 集中交付

按一个完整交付组织到 `task-packages/<完整包ID>/`：采集工程包、算法包、执行证据包等，映射见[任务台账](work-packages.md)。一个包可以覆盖若干相关旧任务 ID，内部连续写代码、测试和实验，不为每个函数、截图或参数试验开包。建议结构：

```text
task-packages/<ID>/
  README.md          负责人、复核人、范围、依赖、状态、复现步骤
  payload/           待合入文件，按总工程目标相对路径组织
  evidence/          测试、日志、截图、数据与失败记录
  manifest.md        文件清单、版本/哈希、目标路径及新增/修改/删除说明
  REVIEW.md          复核结论、通过的准确版本与合入记录
```

只包含本任务成果。已有已发布材料或只读公共输入可以引用明确路径和哈希，不复制出无版本关系的多份源文件。已有总工程文件不因新规则而批量迁走；后续修改在任务包内准备，未通过前不得覆盖总工程活动文件。新规范本身及任务索引的管理更新不视为某个实现任务已验收。

## 交付、复核、合入

1. 负责人在包的工作目录连续开发和自检，实验日志随进度保存；形成完整可交付版本时才设“待复核”。同包内部迭代不需逐次审批，目录与个人开发分支不代表已进入总工程。
2. 台账指定的复核人检查内容、复现与接口兼容性；不通过时写明原因，退回原负责人在包内修订。
3. 复核人明确说“通过”后，记录其身份、日期、工作包版本/提交或文件哈希和通过范围。聊天确认可作为依据，但必须能定位原确认；不得由助手代签或凭测试成功推定通过。
4. **只有复核人负责将通过的准确版本合并到总工程**，包括合入目标目录和目标集成分支。任务作者及作者的执行助手不得自行合入，即使已通过。助手只有获得复核人针对该次合入的明确授权，才可代其执行。
5. 合入前重新核查目标基线、冲突、验证和批准版本；内容有变更或基线变化影响验证时重新复核。合入后记录目标提交/PR、验证结果和状态“已合入”。保留任务包交付记录，避免成为第二套活动开发源。

复核与合入是两个状态，“已通过”不等于“已合入”。同样，草案文档通过只代表该文档通过，不代表对应硬件/算法阶段门通过。所有操作继续遵守阶段门、权限、隐私与仓库保护，禁止绕过评审。
